## 1. Проверка до перезаписи, откат при провале

`deploy/opt-astro/04-frontend-deploy.sh`.

### Было

```
sudo cp snippets → /etc/nginx/snippets/
sudo cp conf.d   → /etc/nginx/conf.d/
sudo cp site     → /etc/nginx/sites-available/
sudo nginx -t
sudo systemctl reload nginx
```

При `set -euo pipefail` неудачный `nginx -t` убивал скрипт **уже после**
перезаписи. В памяти оставался рабочий конфиг, на диске — сломанный. Сайт
продолжал работать и падал при следующем `reload` или перезагрузке, когда
связь с деплоем никто уже не вспомнит.

### Стало

```
бэкап трёх целей → копирование → nginx -t → при провале откат + exit 1
```

**Бэкап всех трёх целей вместе.** Конфиг сайта и зоны `limit_req` из
`conf.d` обязаны откатываться заодно: сайт из репозитория поверх старых зон
(или наоборот) не запустится вовсе — `nginx -t` упадёт на неизвестной зоне.
Частичный откат тут действительно хуже отсутствия.

**Бэкапятся ровно перезаписываемые файлы, а не каталоги целиком.** В
`/etc/nginx/snippets` могут лежать чужие файлы; трогать их нельзя ни при
записи, ни при откате. Список целей собирается из того, что скрипт
собирается положить.

**Откат симметричный.** Файлы делятся на две группы:

| Группа | Что делает откат |
|---|---|
| существовали до запуска | вернуть из копии |
| созданы этим запуском | удалить |

Без второй половины откат был бы неполным: `security-headers.conf`,
которого на сервере сейчас нет, остался бы лежать после неудачной попытки —
и следующий `nginx -t` вёл бы себя не так, как до деплоя.

### `set -e` и откат — то, что вы просили проверить

Да, это было бы проблемой. `sudo nginx -t` голой командой при `set -e`
прерывает скрипт **на месте**, и до отката управление не доходит — ровно
тот сценарий, ради которого всё писалось.

Поэтому проверка вызывается через `if ! sudo nginx -t; then`. В таком
контексте `set -e` не срабатывает по определению (команда в условии), и
откат гарантированно исполняется.

После отката делается **повторный** `nginx -t`. Если и он не проходит —
значит конфиг был сломан ещё до запуска, и об этом говорится прямо, а не
маскируется словом «откачено».

## 2. `client_max_body_size` для PDF

`deploy/opt-astro/nginx/astreatime.conf` — добавлен отдельный location.

### Из чего исходил при выборе 3m

Измерить настоящий размер я не могу — у меня нет браузера, а размер зависит
от конкретной карты. Поэтому от границ, а не «с запасом наугад»:

- Колесо снимается в canvas **1200×1200** и кодируется
  `toDataURL('image/png')` — формат **без потерь**
  (`ChartPage.jsx`, `captureSvgPng`).
- Содержимое — векторная графика на белом фоне: заливки плоские, линии
  тонкие. PNG такое сжимает хорошо; реалистичный диапазон для подобных
  изображений — от полутора сотен килобайт до ~800 КБ.
- Base64 добавляет **ровно треть** (4/3). Итог: примерно **200 КБ – 1.1 МБ**.

Отсюда главное наблюдение: глобальный лимит **1m стоял ровно на верхнем
краю этого диапазона**. Это объясняет, почему отказ выглядел бы не как
постоянная поломка, а как «через раз» — насыщенные карты не проходят,
простые проходят.

**3m** выбран так: покрывает верхнюю границу вдвое и переживает рост
`size` с 1200 до 1600 (площадь ×1.78 → payload ~2 МБ). Больше не берётся,
потому что у соседней ручки со скриншотами стоит `6m` при заявленных 5 МБ,
и уходить за неё ради картинки, которая должна быть в разы меньше,
незачем.

**Как проверить фактический размер** (без деплоя): открыть карту, нажать
«PDF-отчёт», во вкладке Network посмотреть Request Payload у запроса
`.../pdf` — там будет видна длина. Если окажется больше 3 МБ, значение
надо поднять.

### Почему отдельный location, а не правка `/api/`

Id карты стоит **в середине** пути (`/api/v1/chart/{id}/pdf`), префиксом
это не выражается. Поэтому регулярное выражение:

```
location ~ ^/api/v1/chart/[^/]+/pdf$ {
    client_max_body_size 3m;
    ...
}
```

⚠️ **Это первый regex-location в конфиге, и он меняет порядок подбора:**
регулярные проверяются раньше префиксных. Выражение заякорено с обоих
концов (`^...$`), поэтому перехватывает ровно один путь и ничего больше —
`/api/` для остальных ручек не затронут. Директивы проксирования
скопированы из `/api/` без изменений.

Правил только `app/deploy/opt-astro/nginx/astreatime.conf`, как вы указали.
`/opt/astro/nginx/astreatime.conf` не трогал — деплой его не копирует.

## 3. Как прогнать без деплоя

Такого режима **не было**, поэтому добавил: `--nginx-check`.

```bash
cd /opt/astro && ./04-frontend-deploy.sh --nginx-check
```

Что делает: бэкап → копирование → `nginx -t` → **обязательный откат** →
выход. Ни `npm install`, ни `vite build`, ни публикации `dist`, ни
`systemctl reload`. `git pull` тоже пропускается — проверяется тот конфиг,
что сейчас лежит в `app/deploy/opt-astro/nginx/`, так что при
необходимости обновите `app/` заранее.

Коды выхода: `0` — новый конфиг на этом сервере валиден; `1` — не валиден,
всё возвращено.

**Одна оговорка, о которой скрипт предупреждает сам.** Если существует
символическая ссылка `/etc/nginx/sites-enabled/default`, она удаляется и
**не восстанавливается** — это единственное необратимое действие режима.
Восстанавливать её автоматически я не стал: у неё нет копии, и воссоздавать
ссылку на дефолтный сайт, которую деплой всё равно снимет, значит
возвращать состояние, которого никто не хочет.

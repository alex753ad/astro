## 1. Синхронизация `04-frontend-deploy.sh` — `5fe00fd`

`05-update.sh`, список на строке 129: было три файла, стало четыре.
`chmod +x` в `case` тоже расширен — файл исполняемый.

### Ответ на вопрос про порядок: подхватится, но не в первый раз

Вопрос был поставлен точно, и ответ двухуровневый.

**В установившемся режиме — да, в том же запуске.** Синхронизация идёт на
строке 205, вызов `"$FRONTEND_DEPLOY_SCRIPT"` — на строке 327, в самом конце.
04 запускается **отдельным процессом** и читает файл с диска заново, уже
обновлённый. Никакой отложенности нет.

**Первый деплой после этого коммита — нет, и это неизбежно.** На сервере сейчас
лежит старый `/opt/astro/05-update.sh` со списком из трёх файлов. Он скопирует
поверх себя новую версию (`mv -f`, атомарно, старый inode у работающего
процесса сохраняется), но выполняет-то он **свой собственный, старый цикл** —
`04-frontend-deploy.sh` в нём не упомянут. То есть:

- **деплой №1** после этого коммита: приезжает новый `05-update.sh`.
  `04-frontend-deploy.sh` НЕ приезжает.
- **деплой №2**: работает уже новый `05`, `04` приезжает и в том же запуске
  исполняется новая версия.

Вариантов два, оба нормальны:

1. Ничего не делать — второй деплой всё доставит сам.
2. Положить `04` руками один раз, чтобы не ждать (блок команд в разделе
   «Что проверить после доставки»).

**Отдельно: `--frontend-only` синхронизацию не выполняет вообще** (пропускается
весь блок `MODE != frontend`). То есть форсированный запуск всегда исполняет ту
копию 04, что уже лежит на сервере. Это не менялось.

## 3. Метка последнего успешного деплоя — `357ea7e`

### Где лежит

**`/opt/astro/.frontend-deployed-rev`** — рядом с `05-update.sh` и
`docker-compose.yml`, то есть в рабочем каталоге скрипта.

Почему именно там, а не в `app/`: `app/` — рабочая копия git. Посторонний файл
в ней ломает следующий `git pull` — это уже роняло прод дважды, и в CLAUDE.md
под это отведён целый раздел «Файлы, которые портятся сами». `/opt/astro`
репозиторием не является, там такой проблемы нет. В репозиторий метка тоже не
попадает — её там физически не существует, `.gitignore` не нужен.

Содержимое — один коммит-хеш, перевод строки в конце. Пишется атомарно
(`mktemp` + `mv -f`), как и остальные синхронизируемые файлы.

### Как считается флаг

```
есть валидная метка  → git diff <метка> HEAD -- frontend/ deploy/opt-astro/nginx/
нет / пустая / коммита нет в репозитории → frontend_changed=true
```

Метка пишется **только после того, как `04-frontend-deploy.sh` вернул 0**. При
`set -euo pipefail` ненулевой код 04 убивает скрипт прямо на вызове, до записи
управление не доходит — то есть метка не может означать «попытались».

### Первый запуск: лишней пересборки каждый раз не будет — подтверждаю

Метки нет → `frontend_changed=true` → полная пересборка **один раз**. Сразу
после успешного 04 метка записывается, и следующий запуск считает уже реальный
дифф. Проверено локально на шести случаях (нет метки / запись / чтение / дифф
без изменений / мусор в метке / пустая метка / метка старым коммитом) — поведение
ожидаемое в каждом.

Единственный сценарий, где пересборка повторится, — **если запись метки не
удалась**. Тогда в stderr уходит явное `ВНИМАНИЕ: ... следующий запуск
пересоберёт фронтенд заново`, но деплой не падает. Это осознанный выбор:
фронтенд к этому моменту уже доставлен, ронять запуск после успеха нельзя, а
цена ошибки — одна лишняя сборка, а не потерянная правка. Реальный путь сюда
один: файл остался root-овым после запуска `05-update.sh` под `sudo`.

### Что чинится прицепом

- **`--backend-only` больше не теряет изменения фронтенда.** Раньше он честно
  вычислял флаг и выбрасывал его вместе с процессом; теперь метка не двинулась,
  и следующий полный запуск увидит дифф.
- **Падение после `pull`** (не прошёл healthcheck, сработал откат) больше не
  съедает правки фронтенда навсегда.
- Метка **не двигается**, когда фронтенд пропущен как неизменившийся: она
  означает «последнее доставленное», а не «последнее увиденное». Дифф от старой
  метки до нового HEAD по тем же путям всё равно пуст, результат тот же.

## 4. Смешанные права — `3c1fecd`

Оба места приведены к **«всегда `sudo`»**, а не к «нигде `sudo`». Это принципиально:

> «Никогда не sudo» такой поломки не лечит — `deploy` не может удалить
> root-овый каталог. `root` перезапишет любого владельца.

| Место | Было | Стало |
|---|---|---|
| `nginx-backup/<метка>` (строка 144) | `mkdir` без sudo, внутрь `sudo cp -p` | `sudo mkdir -p` |
| `frontend/dist` (строки 124–128) | `mkdir`/`rm`/`cp`/`mv` все без sudo | все пять через `sudo` |

Первое — ровно та поломка, что случилась 31.08.2026: один запуск целиком под
`sudo` сделал `nginx-backup` root-овым, и следующий запуск от `deploy` умирал на
`mkdir` **до копирования конфигов**.

Второе — тот же заряженный капкан, просто ещё не выстреливший: без sudo всё
выглядело согласованно, но после запуска под `sudo` каталог становился
root-овым и `rm -rf "$DIST_TARGET"` от `deploy` не проходил.

Побочный эффект второй правки: `/opt/astro/frontend/dist` станет root-овым при
первом же запуске. Для nginx безразлично — он каталог только читает.

**Пункты 3, 4, 5 из раздела 4 разведки (npm, `git pull`) не трогал**, как и
просили. Там прямого конфликта нет — есть только общее правило «не запускать эти
скрипты под `sudo`», и оно записано в CLAUDE.md и в `deploy/opt-astro/README.md`
явным предупреждением.

## 5. Ротация `nginx-backup` — `43fecb1`

`NGINX_BACKUP_KEEP=10`, функция `prune_nginx_backups`, вызывается сразу после
того, как текущая копия создана и наполнена.

Порядок именно такой намеренно: если удаление вдруг упадёт, копия, ради которой
всё затевалось, уже на месте. Только что созданный каталог считается среди
десяти и остаётся всегда.

Имена — `%Y%m%d-%H%M%S`, поэтому лексикографическая сортировка совпадает с
хронологической и дат парсить не нужно: `find -maxdepth 1 -type d | sort |
head -n -10`. Удаление через `sudo rm -rf` — внутри root-овые файлы от
`sudo cp -p`.

Проверено локально на 13 каталогах: удалено 3, осталось 10, повторный вызов
возвращает 0 и ничего не трогает.

Ротация работает и в режиме `--nginx-check` — он тоже создаёт каталог на каждый
прогон, хотя ничего не доставляет, и именно он копил их быстрее всего.

### Что нельзя проверить без сервера — говорю прямо

Ни один из пяти пунктов не проверен в работе. Проверить локально нечем:

1. **Что 04 подхватывается в том же запуске** — нужен реальный `/opt/astro` с
   двумя копиями скриптов и живой `git pull`.
2. **Что `sudo mkdir` действительно чинит root-овый `nginx-backup`** — нужен
   каталог, испорченный тем самым запуском под `sudo`. Локально нет ни `sudo`,
   ни того каталога.
3. **Что `frontend/dist` корректно пересоздаётся под root** — нужна реальная
   сборка и живой nginx, читающий каталог.
4. **Что метка пишется в `/opt/astro`** — проверена логика функций, не путь и не
   права на запись в боевом каталоге.
5. **Что `nginx -t` проходит на приехавшем конфиге** — конфиг этими правками не
   менялся, но он приедет на прод впервые за четыре недели, и это самый
   рискованный эффект всей работы: до сих пор действующий конфиг (69 строк,
   `/etc/nginx/sites-available/astreatime.conf`) — НЕ копия репозиторного (275
   строк), и ручной блок `location /share/`, добавленный 30.08.2026, будет
   перезаписан.

### Как проверить после доставки

**Перед первым деплоем** — состояние сервера и разбор последствий п. 5.
`--nginx-check` копирует, проверяет и откатывает, ничего не доставляя:

```bash
cd /opt/astro && ls -ld nginx-backup frontend frontend/dist 2>/dev/null; ls -la .frontend-deployed-rev 2>/dev/null; diff -u ./04-frontend-deploy.sh app/deploy/opt-astro/04-frontend-deploy.sh; echo "diff exit=$?"; sudo nginx -T 2>/dev/null | grep -c 'location' ; ./04-frontend-deploy.sh --nginx-check
```

**Если решите не ждать второго деплоя** — положить 04 руками один раз:

```bash
cd /opt/astro && cp app/deploy/opt-astro/04-frontend-deploy.sh .04.tmp && chmod +x .04.tmp && mv -f .04.tmp ./04-frontend-deploy.sh && bash -n ./04-frontend-deploy.sh && echo OK
```

**Если `nginx-backup` остался root-овым после того запуска под `sudo`** — новый
`sudo mkdir -p` отработает при любом владельце, чинить руками не требуется. Но
если хотите вернуть каталог к обычному состоянию:

```bash
cd /opt/astro && sudo chown -R root:root nginx-backup && ls -ld nginx-backup
```

**После первого деплоя** — что доехало и встала ли метка:

```bash
cd /opt/astro && cat .frontend-deployed-rev; git -C app rev-parse HEAD; ls -1 nginx-backup | wc -l; ls -ld frontend/dist; sudo nginx -t; grep -c '' /etc/nginx/sites-available/astreatime.conf; sudo nginx -T 2>/dev/null | grep -A2 'location /share/'
```

Ожидаемое: метка совпадает с `HEAD` репозитория, каталогов в `nginx-backup` не
больше 10, `frontend/dist` принадлежит root, `nginx -t` проходит, в конфиге 275
строк (репозиторная версия приехала), и `location /share/` присутствует — он
есть в репозиторном конфиге, проверить обязательно.

**Проверка, что метка работает** — второй деплой подряд без изменений фронтенда
должен напечатать `Фронтенд и конфиг nginx не менялись — пересборку пропускаю`,
а не собирать заново.

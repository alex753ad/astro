`_required` в `05-update.sh` (`grep` по файлу в рабочем каталоге), и

модерация пройдена, боевой ключ выпущен.

Проверка «ровно одна из двух» после этого стала недостижимой (пустая половина
падает раньше) и **намеренно оставлена** в обоих местах — страхует, если
обязательность когда-нибудь смягчат, и держит отдельную внятную формулировку.
Не удалять как мёртвый код.

Синхронность двух мест проверяется тестом
`TestDeployScriptStaysInSync` (`test_yookassa_required_guard.py`): он читает
`05-update.sh` и требует обе переменные в списке `_required`. Добавляя новый
прод-гвард в `main.py`, не забыть дописать переменную в `PROD_STARTUP_ENV`
(`backend/tests/prod_env.py`) — иначе все subprocess-тесты прод-гвардов начнут
падать по чужой причине.

## Правовые документы — пара .md + .jsx, и она обязана совпадать

`oferta_final.md` ↔ `TermsPage.jsx` и `privacy_final.md` ↔ `PrivacyPage.jsx`.
`.md` программно **не читается** ничем — ни сборкой, ни тестами; синхронизация
ручная, по конвенции из шапки `.jsx`. Правишь одно — правишь оба в том же
коммите.

Что тянется за правкой текста оферты:

1. **`CURRENT_TERMS_VERSION`** (`backend/auth/consent.py`) — дата редакции.
   Используется ТОЛЬКО при создании аккаунта: штампует
   `user.consent_terms_version`. Сравнения с ней нигде нет — ни повторного
   согласия, ни баннера, ни разлогина, механизма не существует. Подъём версии
   ничего не ломает и никого не трогает: старые пользователи сохраняют старый
   штамп, новые получают новый. Читается только в выгрузке `/profile/export`.
2. **Строка «Дата публикации» в `.jsx`** — обязана совпадать с константой,
   это проверяет `test_consent_versions.py`. Разойдутся — упадёт тест.
3. **Комментарий в шапке `.jsx`** с датой редакции исходника.

Меняются все три разом, иначе документ утверждает неправду о самом себе.
Приватность и оферта версионируются **независимо** (две константы) — правка
одной не поднимает вторую.

⚠️ **Версия — это календарная дата, поэтому две редакции одного дня получают
одну версию.** 23.08.2026 так и вышло: утром правился п. 4.3 (сгорание
остатка), вечером п. 4.5 (чек) — обе редакции записаны пользователям как
`2026-08-23`, различить их по `consent_terms_version` нельзя. Ставить завтрашнюю
дату, чтобы «развести» версии, нельзя: документ будет утверждать, что
опубликован в будущем. Если понадобится точность внутри дня — менять сам формат
версии (например добавить порядковый номер редакции), а не подкручивать дату.

**П. 10.1 оферты требует уведомить пользователей за 14 дней** до вступления
изменений в силу, публикацией и письмом. Механизма рассылки в коде нет.
23.08.2026 уведомление не запускалось сознательно: правило про сгорание
остатка работало в коде с самого начала, ничьи условия не ухудшались —
менялась полнота информирования, а не сами условия; плюс пользователей на
проде ещё нет. **Для правки, которая реально меняет условия, это решение не
переиспользовать.**

## Оплата: путь денег до тарифа (24.09.2026)

**Начисление — одна функция `settle_payment`** (`payments/yookassa_router.py`).
Её зовут вебхук, ручка статуса `GET /payments/status/{id}` (экран ожидания)
и ежедневная сверка (`payments/reconcile.py`). Проверки одни на всех:
пользователь есть, тариф продаётся, сумма и валюта по цене на момент СОЗДАНИЯ
платежа, возврата не было. Повтор любой дорожки безопасен — уникальный
`payment_events.inv_id`; гонка двух доставок держится тестом на Postgres
(`test_payment_flow.py`, в CI).

* ⚠️ **Цена — расписание** (`common.PRICE_SCHEDULE` ↔ `TIER_PRICE_SCHEDULE`
  в `constants.js`, сверяет `test_price_sync.py`). Сверка суммы с ЦЕНОЙ НА
  СЕГОДНЯ отбросила бы платёж, созданный до повышения и оплаченный после:
  деньги списаны, тариф не включён. `TIER_PRICES_RUB` остался только для
  админки и считается при импорте — в деньгах его не использовать.
* **Смена цены:** строка расписания с датой не раньше +14 дней (оферта
  п. 10.1) в обоих местах → деплой → `POST /api/v1/payments/admin/price-notice`
  с `dry_run: true`, посмотреть текст → без `dry_run`. Письмо — всем с
  `is_email_confirmed`, включая отписавшихся (уведомление по оферте, не
  реклама), через журнал `email_sent_log` (kind `price_notice`); баннер —
  таблица `announcements` (057), в ленту приложения НЕ ставится: приходит
  после отрисовки и сбил бы прокрутку к сегодняшнему дню.
* **Сверка** — Beat 06:00 МСК, успешные платежи ЮKassa за 7 дней. «Деньги
  есть — записи нет» → начисляет и ВСЕГДА шлёт владельцу «Начислено сверкой»
  (вебхук не дошёл — это сигнал сам по себе). «Запись есть — тарифа нет» →
  только сигнал. Сигналы — инциденты самопроверки.
* **Экран ожидания**: приложение — `PaySheet.jsx` (открывается сам при
  возврате, пока платёж не решён; тексты `mobile/lib/paymentState.js`), веб —
  `/payment/return` (номер платежа сохраняется перед уходом,
  `lib/webPayment.js`). Каждый текст отвечает на «а деньги?».
* **Поддержка** — `POST /feedback` с `screen=payment`: сервер сам приклеивает
  тариф и последние платежи (`_payment_context`).
* ⚠️ **`send_purchase_welcome_task` — `ignore_result=True`, и это несущее.**
  Без него `.delay()` при недоступном Redis переподключается к бэкенду
  результатов БЕСКОНЕЧНО, без исключения — синхронный вызов внутри
  async-вебхука повесил бы весь API. Ровно так локально висели все тесты
  оплаты (TASKS, 23.09.2026) — найдено дампом стека 24.09.2026. Новой задаче,
  которую зовут из запроса, результат которой никто не читает, — тот же флаг.

### Чек по 54-ФЗ покупателю НЕ уходит — ни с веба, ни из приложения

Проверено 24.09.2026 по коду: в платеже нет блока `receipt` (комментарий в
`create_checkout`), путь один для веба и приложения. Причина не в коде:
ЮKassa закрыла «Чеки для самозанятых» 29.12.2025, передать чек некуда. Доход
владелец регистрирует вручную в «Мой налог», оферта п. 4.5 обещает чек по
запросу. Не чинилось — решение владельца; автоматизация возможна только
через API ФНС мимо ЮKassa.

**Помощь владельцу вместо автоматизации (24.09.2026, `payments/receipts.py`):**

* На каждую успешную оплату — одно сообщение «🧾 Чек в „Мой налог“»: сумма,
  дата, услуга («Доступ к сервису Aristea Timeline, тариф „Вега“, 30 дней»),
  email покупателя, номер платежа. Уходит из `settle_payment` там, где платёж
  ВПЕРВЫЕ записан, поэтому вебхук + статус + сверка дают одно сообщение. Уходит
  и когда тариф НЕ выдан (сумма не сошлась, пользователь удалён): доход есть —
  чек нужен.
* ⚠️ **Дата — момент ОПЛАТЫ по Москве** (`payment_events.paid_at`, миграция
  058, из `captured_at` ЮKassa), а не момент обработки: сверка начисляет с
  опозданием до недели, и чек с датой обработки был бы неверным. У записей до
  058 `paid_at` пуст — берётся `created_at`.
* 1-го числа в 09:00 МСК (`tasks.monthly_receipts_summary`) — сводка прошлого
  месяца по московским датам оплаты: все оплаты, возвраты (чеки аннулировать)
  и платежи, которые есть в ЮKassa, но нет в базе.
* Возврат — в сообщении о нём строка «аннулировать чек».

## Промокоды не подключены — целиком, и в чекауте это намеренно

Фича существует кусками, ни один из которых не работает. Проверено по коду и
истории 23.08.2026. Не «чинить UI», не «дописать вызов» — сначала прочитать это.

| Звено | Состояние |
|---|---|
| Поле ввода промокода | Убрано 28.09.2026 вместе с `PaywallModal`/`LyraPaywallModal` (окно предложения теперь `TierOfferModal`, без промокода) |
| `validatePromoCode` → `GET /api/v1/payments/promo-validate` | **Эндпоинта в бэкенде нет вовсе** → всегда 404 → поле ВСЕГДА показывает «Промокод не найден или истёк» |
| `createCheckoutSession` шлёт `promo_code` | Бэкенд принимает и игнорирует: `CheckoutRequest` объявлен с `extra: "ignore"` |
| `POST /admin/coupons/apply` | Вызывающих нет. С 23.08.2026 — `require_admin` |
| `record_promo_usage` | Вызывающих не было **никогда** (`git log --all -S`, функция родилась как `def` в `26ef160`) |

**Игнорирование `promo_code` в чекауте — решение, а не недоделка**
(`yookassa_router.py`, комментарий в `CheckoutRequest`): промокод — вторая
точка, где сумма платежа могла бы разойтись с тем, что реально списала
ЮKassa. Провайдер уведомления не подписывает, сумму мы и так перечитываем из
API и сверяем с `TIER_PRICES_RUB` — вводить в эту сверку ещё одну переменную
без отдельного решения нельзя.

Поэтому «поле промокода не работает» чинится не в UI: пока нет
`promo-validate` и решения по сумме, любой ремонт интерфейса даст
полурабочее состояние. Полный список того, что нужно сделать разом, — в
докстринге `record_promo_usage`.

## Ответы на три вопроса

**Признак точности.** Отдельного булева `is_exact` нет. Есть два поля,
вместе дающие точность:

* `peak_orb` — минимальный орб, которого аспект достигает за весь свой
  проход (в градусах);
* `exact_date` — **момент** точного аспекта с точностью до минуты,
  ISO с временем: `"2026-08-01T00:14"`. Единственное поле во всём ответе,
  где есть время суток, — остальные три даты без времени.

Распределение `peak_orb` по 160 событиям августа (min=0.0001, max=1.4082, медиана=0.3226):

| Диапазон орба | Событий |
|---|---|
| < 0.01° | 11 |
| 0.01–0.1° | 42 |
| 0.1–0.5° | 45 |
| 0.5–1° | 47 |
| > 1° | 15 |

**Сколько из 160 «точные» — зависит от того, какой порог назвать точностью,**
и это решение придётся принять на стороне ленты. Готового ответа ручка не даёт:

| Порог по `peak_orb` | Событий из 160 |
|---|---|
| < 0.05° — практически идеальный аспект | 32 |
| 0.05–0.25° | 41 |
| 0.25–0.5° | 25 |
| 0.5–1.0° | 47 |
| 1.0–1.5° | 15 |

Больше 1.5° нет ни одного, и это не случайность: движок считает орб по
таблице `TRANSIT_ORBS` (`backend/transit/engine.py`) — соединение, квадрат
и оппозиция до 2.0°, секстиль и трин до 1.5°. Всё, что шире, событием не
становится вовсе.

⚠️ **`exact_date` — не всегда момент внутри запрошенного окна.** У 13 из 160
августовских событий он приходится на июль или сентябрь: это проходы,
которые в августе только начались или ещё не закончились. То есть
`exact_date` — момент точки самого аспекта, а не «точка внутри выдачи»,
и сортировка ленты по нему выкинет часть событий за пределы своего же окна.

**Орб.** Есть, `peak_orb`, но только орб В ТОЧКЕ — текущего орба на
произвольную дату в ответе нет. Параметр `max_orb` в запросе есть (см. ниже).

**Длительность.** Есть, интервалом `start_date` … `end_date`, плюс
`peak_date` внутри. Отдельного поля с числом дней нет — считать самим.

| Длительность, дней | Событий |
|---|---|
| 0 | 104 |
| 1 | 18 |
| 2 | 7 |
| 3 | 11 |
| 4 | 10 |
| 5 | 1 |
| 6 | 2 |
| 11 | 1 |
| 14 | 1 |
| 18 | 2 |
| 27 | 1 |
| 33 | 2 |

**Тип аспекта.** Поле `aspect_type`, строка. Все встретившиеся значения
за август и сентябрь:

| `aspect_type` | Событий (авг+сен) |
|---|---|
| `square` | 85 |
| `trine` | 80 |
| `sextile` | 72 |
| `opposition` | 37 |
| `conjunction` | 35 |

**Как отличить мажорные от прочих.** Признака в ответе нет — но он и не нужен:
**минорных аспектов не существует в выдаче по построению.** Движок считает
ровно пять аспектов, это вся таблица `TRANSIT_ORBS` в
`backend/transit/engine.py`:

```python
TRANSIT_ORBS = {
    "conjunction": 2.0,
    "sextile":     1.5,
    "square":      2.0,
    "trine":       1.5,
    "opposition":  2.0,
}
```

Полусекстиль, квинконс, полуквадрат не вычисляются вовсе, поэтому фильтровать
по мажорности нечего и незачем. Но и опереться на `aspect_type` как на «вес»
нельзя: все пять равноправны, порядка важности между ними нет.

Что действительно есть про важность — `significant`, и это **не про аспект**:

на free под блюром витрины.

Тарифно-независимо — то есть поле приходит одинаковым всем тарифам, и на
платном оно смысла не несёт.

## Границы окна: что попадает в выдачу

Проверено по августовскому ответу — окно обрезает края несимметрично:

| Факт | Значение |
|---|---|
| Событий с `start_date` раньше `from_date` | **0** — начало всегда обрезано по границе окна |
| Событий, начинающихся ровно в `from_date` | 19 — это обрезанные, шедшие ещё в июле |
| Событий с `end_date` позже `to_date` | **11** |
| Самый поздний `end_date` при запросе по 31.08 | **2026-09-03** |

Причина в коде: скан идёт до `to_date + 3 дня`
(`scan_end = ... + timedelta(days=3)`), чтобы поймать закрытие окон, а старт
скана — ровно `from_date`. Отсюда асимметрия.

⚠️ Для ленты это значит, что **`start_date` нельзя показывать как «начало
транзита»** — у части событий это просто дата, с которой начинался запрос.
Настоящее начало у обрезанных событий неизвестно; отличить обрезанное от
настоящего можно только сравнением `start_date == from_date`.

## Как заданы границы периодов

**Строкой для показа человеку, не датами.** Ни одного ISO-поля внутри
периодов нет — ни в `month_sections`, ни в `week_days`, ни в `longterm`.

| Блок | Поле границы | Реальное значение | Формат |
|---|---|---|---|
| `month_sections[].periods[]` | `period` | `"07.08 — 06.09"` | `дд.мм — дд.мм`, **без года** |
| `longterm[]` | `period` | `"14.07.2025 — 05.09.2026"` | `дд.мм.гггг — дд.мм.гггг`, с годом |
| `week_days[]` | `date` / `time` | `"30.08 Вс 15:56"` / `"01.09 Вт 09:52"` | дата + день недели + время, без года |
| `retrogrades[]` | `date` | `"10.09"` | `дд.мм`, без года |
| `week_nav` | `week_start` / `week_end` | `"2026-08-31"` / `"2026-09-06"` | **единственный ISO во всём планере** |

Имена полей у `week_days` вводят в заблуждение: `date` — это НАЧАЛО
периода со временем, `time` — КОНЕЦ периода со временем. Оба содержат и
дату, и время, ни одно не является только датой или только временем.

## Откуда берётся длительность

Отдельного поля длительности нет нигде. Её можно только вычислить из
строки `period`, разобрав её парсером и **достав год откуда-то ещё** —
в месячных секциях года нет вовсе. Для периода `"07.08 — 06.09"` год
берётся из `month_title` (`"Планер на сентябрь 2026"`) или из `week_nav`.

Отдельная ловушка: период месячной секции спокойно выходит за границы
запрошенного месяца в обе стороны — `"07.08 — 06.09"` в ответе на сентябрь.
То есть это не «периоды внутри месяца», а «периоды, пересекающие месяц».

то, что нужно для размытых блоков: каркас известен (когда, какой дом,

## Параметры, диапазон, пагинация

| Вопрос | Ответ |
|---|---|
| Какие параметры принимает | `month_offset` (int, по умолчанию 0), `week_offset` (int, опционально) |
| Произвольный диапазон или календарный месяц | **Только календарный месяц**, и только смещением от текущего. Дат на вход не принимает вовсе — ни `from_date`, ни `year`/`month`. Внутри недели — `week_offset`, тоже смещение, не даты |
| Пагинация | **Нет.** Весь месяц одним ответом; `week_nav.total_weeks` = 5 — это навигация по неделям внутри месяца, а не постраничность |

Тарифный горизонт проверяется по `month_offset`. На free разрешён только 0:

```json
{
  "detail": "Планер доступен на 0 мес. вперёд на вашем тарифе (запрошено 1)."
}
```

Отдельно: при неизвестном времени рождения ручка отдаёт не периоды, а
`{"planner": {"error": "Время рождения неизвестно — планер недоступен."}}`
(видно в коде `main.py`; на этой карте время известно, поэтому боем не
воспроизводилось).

## Содержимое каждого поля

### `year`, `month`

Числа, эхо запроса: `2026`, `9`. Если параметры не
переданы — подставляется текущий месяц по времени сервера (UTC).

### `current_moon`

```json
{
  "sign": "Близнецы",
  "degree": 15.9
}
```

Два поля: знак по-русски и градус. **Это положение Луны на СЕЙЧАС, а не на
запрошенный месяц** — при запросе марта 2027 приходит ровно то же самое
значение, что и при запросе сентября 2026. Для ленты поле бесполезно, если
лента не про «сегодня».

### `phases`

Список, 2 элемента за сентябрь. Полностью:

```json
[
  {
    "date": "2026-09-11",
    "time": "06:27 GMT+3",
    "type": "new_moon",
    "planet": "Moon",
    "sign": "Дева",
    "emoji": "🌑",
    "description": "Новолуние в Дева"
  },
  {
    "date": "2026-09-26",
    "time": "19:49 GMT+3",
    "type": "full_moon",
    "planet": "Moon",
    "sign": "Овен",
    "emoji": "🌕",
    "description": "Полнолуние в Овен"
  }
]
```

Обычно 2 за месяц (новолуние + полнолуние), иногда 3 — проверено по 24
месяцам подряд: 3 фазы в мае 2026 и августе 2027, в остальных 22 месяцах — 2.

### `daily_signs`

Список по одному элементу на каждый день месяца (30 за сентябрь,
31 за август, 28 за февраль — то есть ровно длина месяца). Первые три:

```json
[
  {
    "date": "2026-09-01",
    "sign": "Телец",
    "longitude": 32.28
  },
  {
    "date": "2026-09-02",
    "sign": "Телец",
    "longitude": 46.12
  },
  {
    "date": "2026-09-03",
    "sign": "Близнецы",
    "longitude": 60.12
  }
]
```

Три поля: дата, знак Луны, эклиптическая долгота. Времени входа в знак
здесь нет — только снимок на день. Момент перехода Луны из знака в знак
этой ручкой не отдаётся вовсе (он есть в планере, в `week_days`, но там
это дома, а не знаки, и на free всё закрыто).

### `eclipses`

За сентябрь 2026 — **пустой список**. Затмения редки, поэтому структура
показана по августу 2026 (два затмения):

```json
[
  {
    "date": "2026-08-12",
    "time": "17:45 UTC",
    "type": "solar",
    "kind": "total"
  },
  {
    "date": "2026-08-28",
    "time": "04:12 UTC",
    "type": "lunar",
    "kind": "partial"
  }
]
```

⚠️ **Набор полей у затмения ДРУГОЙ, чем у фазы.** У фазы семь полей
(`date`, `time`, `type`, `planet`, `sign`, `emoji`, `description`), у
затмения — четыре: `date`, `time`, `type`, `kind`. Нет ни `description`,
ни `emoji`, ни `sign`. Подпись для ленты придётся собирать самим из
`type` + `kind`.

⚠️ **И пояс времени у них разный.** Фаза: `"06:27 GMT+3"`. Затмение:
`"17:45 UTC"` — **UTC**. Это известная открытая находка
3.7 из CLAUDE.md, подтверждённая здесь боем: события одного календаря
подписаны разными поясами, расхождение до 3 часов, у события около полуночи
уводит и дату.

Значения `type`/`kind` за проверенные 24 месяца:

| `type` | `kind` | Примеры дат |
|---|---|---|
| `lunar` | `partial` | 2026-08-28 |
| `lunar` | `penumbral` | 2027-02-20, 2027-07-18, 2027-08-17 |
| `lunar` | `total` | 2026-03-03 |
| `solar` | `annular` | 2026-02-17, 2027-02-06 |
| `solar` | `total` | 2026-08-12, 2027-08-02 |

### `solar_events`

```json
[
  {
    "date": "2026-09-23",
    "time": "03:05 GMT+3",
    "type": "equinox_autumn",
    "emoji": "🍂",
    "description": "Осеннее равноденствие"
  }
]
```

Равноденствия и солнцестояния, по одному в квартал (проверено: есть в
марте, июне, сентябре, декабре, в остальных месяцах список пуст). Поля как
у фазы, но без `planet` и `sign`. Пояс — `GMT+3`, как у фаз.

## Параметры, диапазон, пагинация

| Вопрос | Ответ |
|---|---|
| Какие параметры принимает | `year` (int), `month` (int). Оба необязательные — без них текущий месяц по UTC |
| Произвольный диапазон или календарный месяц | **Только календарный месяц целиком.** Диапазон дат задать нечем |
| Пагинация | **Нет** и не нужна — месяц целиком это ~35 элементов |

⚠️ **Тарифного гейта на этой ручке нет вообще.** Флаг `lunar_months`
(free — 1 месяц) на бэкенде не проверяется: запрос марта 2027 **без
всякой авторизации** отдал 200 и полный ответ (проверено, статус
200, поля ['current_moon', 'daily_signs', 'eclipses', 'month', 'phases', 'solar_events', 'year']).
Ручка публичная, `user` в ней не участвует. Для ленты это скорее удобно —
но на это нельзя закладываться как на решение, это незакрытый гейт.

# 4. Чего для ленты не хватает

Только перечень фактов. Правок бэкенда не предлагаю.

### 4.1. Нет единого времени, по которому можно отсортировать

Три ручки описывают время тремя несовместимыми способами:

| Источник | Формат времени | Пояс |
|---|---|---|
| Транзиты, `exact_date` | `2026-08-01T00:14` — ISO с минутами | не указан |
| Транзиты, `start/peak/end_date` | `2026-08-01` — ISO без времени | — |
| Планер, `period` | `07.08 — 06.09` — строка, **без года** | — |
| Планер, `week_days.date` | `30.08 Вс 15:56` — строка с днём недели | — |
| Лунный, `phases.time` | `06:27 GMT+3` — время отдельной строкой | GMT+3 |
| Лунный, `eclipses.time` | `12:11 UTC` — время отдельной строкой | **UTC** |

Чтобы сложить это в одну ленту, придётся писать три разных парсера и
самим достраивать год для планера и пояс для затмений.

### 4.2. Нет признака важности, общего для трёх источников

* У транзита есть `significant` (bool) — но только у транзита.
* У планера признака важности нет вовсе; есть `locked` — это про тариф.
* У лунных событий нет ни того, ни другого: новолуние, затмение и
  равноденствие приходят без веса. Различить их можно только по `type`.

Общей шкалы, по которой транзит можно сравнить с затмением, нет.

### 4.3. Нет мажорности аспекта

`aspect_type` — строка. Классификация «мажорный/минорный» в ответе
отсутствует; сегодня в выдаче встречаются только пять мажорных значений,
но это наблюдение по двум месяцам, а не гарантия схемы.

### 4.4. Нет окна «неделя назад — месяц вперёд» ОДНИМ запросом на всё

По транзитам такое окно работает (проверено, 200). Но:

* планер принимает только `month_offset` — окно, пересекающее два месяца,
  это два запроса, и границы периодов всё равно приедут строками без года;
* лунный календарь принимает только `year`+`month` — то же самое, два
  запроса на окно через границу месяца.

То есть лента на произвольное окно — это минимум 1 + 2 + 2 = **пять
запросов**, а не один.

### 4.5. Нет пагинации ни в одной из трёх ручек

Транзиты за месяц — 160 событий одним массивом, из них 114 лунных.
Ограничить выдачу можно только `planet` (одна планета) и `max_orb`.
Отсечь «только медленные планеты» одним параметром нечем — `planet`
принимает одно имя, не список.

### 4.6. У транзита нет текста

В событии только астрономия: планеты, знаки, градус, аспект, даты.
Ни заголовка, ни описания. Текст живёт в отдельной SSE-ручке
`/transits/event/interpret`, и он платный (квота `transit_ai`, у free — 0).
В планере текст наоборот приходит сразу (`theme`, `groups[].items`), у
лунных событий — `description`. То есть три источника ленты дают текст
тремя разными способами, а один из трёх — за деньги и потоком.

### 4.7. Идентификаторов событий нет

Ни у транзита, ни у периода планера, ни у лунного события нет `id`.
Ключ для дедупликации, «прочитано», закладок или дозагрузки придётся
собирать самим из полей — а у планера собирать его не из чего, кроме
строки периода и номера дома.

### 4.8. `current_moon` не следует за запрошенным месяцем

Всегда «сейчас», независимо от `year`/`month`. Если лента листается в
прошлое или будущее, это поле показывает не то, что вокруг него.

### 4.9. Границы транзита обрезаны окном, и это никак не помечено

`start_date` обрезается по `from_date` (19 событий из 160 за август),
`end_date` уезжает на 3 дня дальше `to_date` (11 событий). Флага «обрезано»
нет. Лента, листаемая окнами, будет показывать одному и тому же транзиту
разное начало в зависимости от того, с какой даты запрошено окно, — а
дедуплицировать его будет не по чему (см. 4.7, идентификаторов нет).

### 4.10. Нет текущего орба на дату

`peak_orb` — орб в точке максимального сближения за весь проход. Насколько
аспект силён именно сегодня, из ответа не выводится: для этого нужны
эфемериды на дату, которых в выдаче нет. Сортировать ленту «по силе на
сейчас» нечем.

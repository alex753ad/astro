## 🔴 №1. Celery-воркера не существует — часть функций молча не работает

**Критичность: критическая. Не исправлено (нужно ваше решение по архитектуре).**

`backend/celery_app.py` настроен полностью, включая `beat_schedule`. Но в
`docker-compose.yml` есть только `postgres`, `redis`, `api`, `bot`, `uptime-kuma`.
Ни воркера, ни beat. `start.sh` умеет ровно два режима: `uvicorn` и `python -m bot.pilot_bot`.

Значит **каждый вызов `.delay()` кладёт задачу в Redis, и её никто никогда не берёт**:

| Точка вызова | Что не работает для пользователя |
|---|---|
| `crm/dashboard_router.py:216` | Рассылка клиентам из CRM. API отвечает `{"queued": true, "recipients": 42}` — интерфейс показывает успех, писем нет. Premium-функция. |
| `main.py:1950` | `POST /chart/{id}/transits/async` возвращает `task_id`, фронт опрашивает `pollTask` и через 120 секунд бросает `Task timeout`. Это рекомендованный путь для периодов больше 3 месяцев. |
| `main.py:705` | `schedule_retention_emails` — письма 2-го и 7-го дня. Частично дублируются `/internal/onboarding-emails`, но и он не вызывается (см. №6). |
| `onboarding_router.py:168` | Проверка лунных возвращений. |
| `payments/stripe_service.py:328-332, 572` | Legacy-путь, неактуален. |

Задачи копятся в Redis без ограничения — при `--save 60 1` они переживают рестарт
и растут бесконечно.

**Как чинить.** Либо поднять воркер и beat (`SERVICE_ROLE=worker` в `start.sh` +
два сервиса в compose — образ уже собран, менять нечего), либо честно убрать Celery
и перевести оставшиеся три вызова на внутренний планировщик из `main.py`, который
уже работает и обслуживает push-тик и еженедельный дайджест. Второе дешевле:
`asyncio`-планировщик в приложении уже есть, а Celery в этой конфигурации даёт
только иллюзию фоновой обработки. Отдельно: `POST /transits/async` в любом случае
нужно либо починить, либо убрать из API — сейчас он гарантированно приводит к
ошибке на экране.

## 🔴 №2. Лимитер роняет весь API при недоступном Redis

**Критичность: критическая. Исправлено.**

`SlowAPIMiddleware` (добавлен в рамках H-5) проверяет лимит на **каждом** запросе.
Когда Redis недоступен, ошибка хранилища всплывает наружу, slowapi передаёт её в
обработчик `RateLimitExceeded`, а тот обращается к `exc.detail`:

```
AttributeError: 'ConnectionError' object has no attribute 'detail'
```

Результат — **500 на любой запрос, включая `/health`**. Докер-healthcheck начинает
падать, `05-update.sh` откатывает деплой, uptime-kuma шлёт алерт: отвал кэша
превращается в полный отказ сервиса. Пока лимит висел декораторами на 22 ручках из
141, падали только они — глобальный middleware поднял это до тотального отказа.

Воспроизведено: тесты `test_debug_routes.py::TestDebugRoutesEnabled` поднимают
приложение в подпроцессе без Redis и падают именно на этом.

**Исправление:** `swallow_errors=True` и `in_memory_fallback_enabled=True` у `Limiter`
(`backend/limiter.py`). Fail-open здесь оправдан: rate limiting — не контроль
доступа, а защита от перебора, и жёсткий рубеж для неё теперь стоит в nginx
(`limit_req`), который работает независимо от Redis.

## 🔴 №3. Все письма пилотной программы не отправляются

**Критичность: критическая (для пилота). Не исправлено — одна строка, но это меняет поведение продукта.**

`backend/pilot/cron.py`, три места (155, 199, 245):

```python
asyncio.get_event_loop().run_until_complete(send_pilot_farewell(...))
```

`_process()` синхронная и вызывается из `async def pilot_tick` (строка 264), то есть
**внутри уже запущенного event loop**. Воспроизведено:

```
RuntimeError: This event loop is already running
```

Исключение ловится соседним `except Exception` и уходит в `logger.warning`. А сразу
после — безусловный `_mark(db, user.id, "dormant5", cohort)`, который записывает в
`push_sent_log`, что письмо отправлено. **Дедупликация не даст повторить попытку
никогда.**

Не доходят: `farewell` (прощание с офером продления), `dormant5/10/14` (возврат
неактивных), `end_of_month` (exit-survey). Пуши в тех же ветках работают — они
синхронные, поэтому со стороны выглядит, будто механика жива.

**Как чинить.** Сделать `_process` асинхронной и заменить три `run_until_complete`
на `await` (`pilot_tick` уже `async`). И перенести `_mark` под успешную отправку —
иначе следующий такой сбой снова «съест» письмо навсегда.

Тот же паттерн в `backend/tasks.py` (14 мест) и `stripe_service.py` (3) сейчас
безвреден только потому, что Celery не запущен (см. №1). Если воркер поднимут —
там он тоже работает лишь до Python 3.13; на 3.14 `get_event_loop()` без текущего
цикла бросает `RuntimeError` вместо предупреждения.

## 🟠 №4. Оплата могла списаться без активации подписки

**Критичность: высокая. Исправлено.**

Реализация M-1 (таблица `payment_events`) коммитила запись о платеже **до**
активации:

```python
db.add(PaymentEvent(...)); db.commit()      # ← отдельная транзакция
...
activate_subscription(...)                   # упало → 500
```

Комментарий в коде утверждал: «Robokassa повторит вызов, и повтор пройдёт штатно».
На деле повтор попадал в ветку `IntegrityError` → `«duplicate ignored»` → `OK{InvId}`.
Деньги списаны, подписки нет, ретраи исчерпаны, автоматически починить нечем — только
руками через `set-tier`.

**Исправление:** `db.flush()` вместо `commit()`, активация, затем общий `commit`;
`db.rollback()` на ошибке активации. Ровно то, что предписывал исходный аудит
(«вставка в той же транзакции, что и `activate_subscription`»). Добавлены два теста
на этот сценарий: `TestActivationFailureIsRetryable`.

## 🟠 №5. 17 тестов молча не выполнялись

**Критичность: высокая. Исправлено.**

`backend/tests/pytest.ini` лежит в каталоге, который передаётся pytest аргументом
(`pytest backend/tests/`), поэтому pytest берёт **rootdir = backend/tests** и читает
конфиг оттуда. `[tool.pytest.ini_options]` из `pyproject.toml` — включая
`asyncio_mode = "auto"` — не применяется вовсе.

Async-тесты без явного `@pytest.mark.asyncio` возвращали корутину, которую никто не
ждал. На pytest 8 (как в CI) это **проходило как passed** с предупреждением
`coroutine was never awaited`. Весь `test_ai_cascade.py` — каскад AI, ретраи,
проверка бюджета, кэш — числился зелёным, не проверяя ничего.

**Исправление:** `asyncio_mode = auto` в `backend/tests/pytest.ini` с комментарием,
почему настройку приходится дублировать. После этого прогон вырос с 543 до 609
реально выполненных тестов.

Заодно: `test_ai_cascade.py::_run` использовал `asyncio.get_event_loop()` — на
Python 3.12 это DeprecationWarning, на 3.14 `RuntimeError`. Заменено на `asyncio.run`.

## 🟠 №7. Расчёт транзитов блокирует весь процесс на 1–4 секунды

**Критичность: высокая. Не исправлено.**

Замерено на этой машине (`data/ephe`, pyswisseph):

| Операция | Время |
|---|---|
| `calculate_full_chart` | 2 мс |
| `calculate_transits`, 3 месяца | **1 030 мс** (443 события) |
| `calculate_transits`, 12 месяцев | **3 940 мс** (1 655 событий) |

Всё это — синхронный CPU-bound код, вызываемый напрямую из `async def`
(`main.py:1017 get_transits`, `1620 get_daily_forecast`, `1506 get_weekly_forecast`).
`start.sh` запускает uvicorn **без `--workers`**, то есть один процесс и один event
loop. На время расчёта встают все остальные запросы: чужие SSE-стримы, `/health`,
статика через API.

Пять параллельных годовых запросов — двадцать секунд полной остановки. Docker
healthcheck (`timeout: 5s`, `retries: 5`) в такой ситуации может уронить контейнер
в unhealthy и, если это происходит во время деплоя, вызвать откат.

К этому же классу относится синхронный SQLAlchemy: каждый `db.query(...)` в `async def`
блокирует loop на время round-trip к Postgres.

**Как чинить**, по возрастанию стоимости:
1. Обернуть тяжёлые вызовы в `await asyncio.to_thread(...)` — GIL отпускается на
   время работы C-расширения pyswisseph, так что для транзитов это даёт настоящий
   параллелизм. Правка на несколько строк.
2. Поднять `uvicorn --workers 2..4` (памяти хватает, лимит контейнера 1.5 ГБ).
3. Кэш транзитов уже есть (`transit_cache`) — стоит проверить hit rate: при
   промахе на каждый запрос п.1 обязателен.

## 🟡 №10. Задачи и планировщик умирают вместе с одним процессом

**Критичность: средняя. Не исправлено.**

`_scheduler_loop` живёт внутри api-контейнера и запускается в `lifespan`. Отсюда:
- при `--workers > 1` (см. №7) планировщик стартует **в каждом воркере** —
  push-тик и дайджест уйдут в N копий. Дедупликация по `push_sent_log` спасёт от
  дублей писем, но не от N-кратной нагрузки и гонок;
- переменная `last_weekly_digest` хранится в памяти процесса: рестарт в понедельник
  между 06:00 и 07:00 UTC отправит дайджест повторно;
- условие `now.hour == 6` при интервале 15 минут срабатывает четыре раза за час —
  спасает только `last_weekly_digest`, то есть та самая переменная в памяти.

**Как чинить.** Признак «дайджест за эту неделю отправлен» перенести в БД
(`push_sent_log` уже подходит по схеме), а запуск планировщика привязать к явному
`SCHEDULER=on` ровно на одном экземпляре.

## 🟡 №12. Ошибка активации подписки не видна операционно

**Критичность: средняя. Не исправлено.**

## 🔵 №13. `JSON.stringify` в `dangerouslySetInnerHTML`

`HomePage.jsx:65`, `LunarCalendarPage.jsx:240`, `ZodiacPage.jsx:108` — разметка
schema.org вставляется через `dangerouslySetInnerHTML`. `JSON.stringify` не
экранирует `</script>`. Сейчас данные статические (FAQ, описания знаков), пользователь
на них не влияет, и CSP `script-src 'self'` не даст выполниться инлайну — но если в
schema.org когда-нибудь попадёт имя пользователя или текст отзыва, это станет XSS.
**Решение:** `.replace(/</g, '\\u003c')` после `stringify`.

# Что сделано хорошо

  механизм гасит ссылки сброса пароля и подтверждения email.

## Что именно копируется

`05-update.sh:242` вызывает `04-frontend-deploy.sh`, если в `git pull`
затронут `frontend/` (либо при `--frontend-only`). Тот в блоке `:113-129`
делает:

| Источник в репозитории | Назначение на сервере |
|---|---|
| `nginx/snippets/*.conf` (`csp.conf`, `security-headers.conf`) | `/etc/nginx/snippets/` |
| `nginx/conf.d/00-astro-hardening.conf` | `/etc/nginx/conf.d/` |
| `nginx/astreatime.conf` (235 строк) | `/etc/nginx/sites-available/astreatime.conf` |

Затем `ln -sf` в `sites-enabled`, удаление `sites-enabled/default`,
`nginx -t`, `systemctl reload nginx`.

Копирование **безусловное** (`sudo cp`), без резервной копии и без
сравнения с тем, что лежит на сервере.

## Риски, по убыванию ущерба

### 1. `client_max_body_size 1m` на уровне http — PDF с колесом карты начнёт отбиваться 413

**Самый вероятный из ощутимых.**

`00-astro-hardening.conf:52` объявляет `client_max_body_size 1m` глобально.
Повышение до `6m` есть **ровно в одном** location — `/api/v1/feedback`
(`astreatime.conf:121`). Location `/api/` его не переопределяет, то есть
наследует 1 МБ.

А `POST /api/v1/chart/{id}/pdf` шлёт в теле `wheel_png` — колесо карты,
снятое `captureChartPng(..., size = 1200)` и закодированное в base64.
PNG 1200×1200 после base64 — сотни килобайт, у насыщенных карт легко за
мегабайт. Тогда nginx вернёт 413 **до приложения**, и человек увидит
«Не удалось сгенерировать PDF: HTTP 413» (тело 413 у nginx — HTML, `detail`
оттуда не читается).

Проверяется без деплоя, прямо сейчас: снять карточку в браузере и
посмотреть длину `wheel_png` в запросе на вкладке Network.

### 2. `nginx -t` может упасть, а файлы уже скопированы

В скрипте `set -euo pipefail` (`:4`), и порядок такой: сначала `cp` всех
трёх мест, потом `nginx -t`, потом `reload`. Если проверка не пройдёт,
скрипт умрёт **после** копирования.

Результат — расхождение: в памяти nginx работает старый конфиг, на диске
лежит новый и сломанный. Сайт продолжает работать, но **следующий
`systemctl reload nginx` или перезагрузка сервера положат его**, и связь с
деплоем к тому моменту потеряется.

Наиболее вероятная причина падения проверки — `default_server`. Конфиг из
репозитория объявляет два таких блока (`:17-19` на 80 и `:24-26` на 443,
оба `server_name _`). Если на сервере есть ещё один `default_server` на тех
же портах — nginx откажется с «a duplicate default server». Скрипт снимает
только `sites-enabled/default`; всё, что лежит в `conf.d/` или под другими
именами, он не видит.

Проверить заранее:

```bash
sudo grep -rn "default_server" /etc/nginx/ | grep -v sites-available/astreatime.conf
```

### 3. TLS-политика ужесточается для всех виртуалхостов сразу

`00-astro-hardening.conf:11-15` кладёт на уровень http:

- `ssl_protocols TLSv1.2 TLSv1.3` — TLS 1.0/1.1 отключаются;
- только AEAD-шифры (никаких CBC);
- `ssl_prefer_server_ciphers off`.

Само по себе это улучшение, но действует **на весь nginx**, а не только на
astreatime.ru. Если на сервере есть другой сайт, доступный со старых
клиентов, он это заметит.

Плюс `ssl_stapling on` с `resolver 127.0.0.53` (`:23-26`). Если
systemd-resolved не слушает этот адрес, стаплинг не заработает и в
`error.log` пойдут предупреждения — не фатально, но лог зашумит.

### 4. Появляются лимиты запросов там, где их не было

`00-astro-hardening.conf:36-38` заводит зоны, конфиг сайта их применяет:

| Путь | Лимит |
|---|---|
| `/api/v1/auth/` | 1 r/s, burst 10 |
| `/api/` и `/api/v1/feedback` | 10 r/s, burst 20, nodelay |
| `/share/` | 2 r/s, burst 10, nodelay |
| весь сервер | `limit_conn perip 30` |

Ключ — `$binary_remote_addr`. Опасное место: **пользователи за общим NAT**
(офис, мобильный оператор) считаются одним адресом. 1 r/s на `/api/v1/auth/`
при нескольких людях с одного адреса даст 429 на входе.

`limit_conn perip 30` тоже стоит держать в голове: SSE-стримы держат
соединение открытым, а вкладок у человека может быть несколько.

### 5. Ваш ручной блок `/share/` будет заменён — но это не потеря

Конфиг из репозитория **содержит** `location /share/` (`:160-176`) с тем же
`proxy_pass http://127.0.0.1:8000` плюс `limit_req zone=share`. Зона
приезжает из `conf.d`, который копируется **раньше** сайта, — то есть на
момент `nginx -t` она объявлена.

То, чего вы опасались (потеря `/share/` и отказ nginx из-за необъявленной
зоны), при полном копировании всех трёх мест **не произойдёт**. Опасно
другое — копировать что-то одно: если положить только сайт, не положив
`conf.d`, nginx упадёт на неизвестной зоне.

Единственная реальная потеря — если ваш ручной блок отличается от
репозиторного чем-то, что вы добавили сегодня по ходу. Стоит сравнить до
деплоя:

```bash
sudo diff -u /etc/nginx/sites-available/astreatime.conf \
  /opt/astro/app/deploy/opt-astro/nginx/astreatime.conf | head -60
```

### 6. CSP — риск низкий сейчас и высокий при включении

`csp.conf:36` отдаёт **`Content-Security-Policy-Report-Only`**, боевая
строка `:37` закомментирована. Браузер ничего не блокирует, только пишет
нарушения в консоль. То есть приезд CSP сам по себе ничего не сломает.

Что стоит знать про неё заранее:

- **Подключена только в двух местах** — `:220` и `:232` (`= /index.html` и
  `location /`). На ответы API заголовок не идёт, и это нормально.
- **`script-src` без `'unsafe-inline'`** — главная ценность политики. Ради
  этого регистрация service worker вынесена из `index.html` в `main.jsx`, а
  счётчик Метрики грузится из бандла (`analytics.js`), а не инлайновым
  сниппетом из её кабинета.
- **Метрике нужны ровно три источника** — `script-src`, `connect-src`,
  `img-src` (пиксель, когда XHR недоступен). Все три в строке есть. В
  Report-Only отсутствие любого было бы незаметно: счётчик не падает, а
  молча недосчитывает визиты.
- **`style-src` с `'unsafe-inline'`** оставлен осознанно: React и Tailwind
  ставят `style=` на элементы.

Главный риск отложенный: между приездом Report-Only и включением боевой
никто не собирает отчёты. `report-uri`/`report-to` в политике нет, то есть
нарушения видны **только в консоли того браузера, где они произошли**.
Собрать их с реальных пользователей нельзя — значит «подержать 1–2 недели и
посмотреть» из комментария в файле на практике не сработает: смотреть будет
нечего, кроме своей вкладки.

## Что делать перед возобновлением деплоя фронтенда

Порядок, от дешёвого к дорогому:

1. `diff` живого конфига с репозиторным (команда выше) — увидеть, что
   именно изменится.
2. `grep default_server` по `/etc/nginx/` — исключить падение `nginx -t`.
3. Снять `wheel_png` в браузере и посмотреть его размер — оценить риск 413.
4. Сохранить копию рабочего конфига: `sudo cp /etc/nginx/sites-available/astreatime.conf ~/astreatime.conf.bak`
5. Прогнать деплой с `--frontend-only` в момент, когда вы у консоли.

Чинить что-либо из перечисленного я не стал — вы просили разбор, и три из
шести пунктов решаются не кодом, а проверкой на сервере.

# Спецификация экрана «Ещё» (мобильное приложение)

Версия 1.0, 06.09.2026. Составлена по прототипу `aristea-mobile.html`
(ЭКРАН 3) и разведке `MORE_API_RECON.md` — все утверждения о данных ниже
опираются на боевые ответы оттуда, а не на схемы. Формат документа — тот
же, что в `SPEC_CHART_SCREEN.md`.

Смежные документы: `SPEC_FEED_SCREEN.md`, `SPEC_CHART_SCREEN.md`.

---

## 1. Что это за экран

Третья вкладка приложения. Личный кабинет: кто вошёл, какой тариф,
какие карты сохранены, и вход в четыре раздела помельче (история,
друзья, уведомления, настройки) плюс строку-ссылку на выгрузку данных
на сайте (решение по ней — §6.2, пункта меню для неё нет).

Сегодня на вкладке — только переключатель темы (`MoreScreen.jsx`,
`ThemeToggle`). Он остаётся на месте, весь список ниже — новый.

---

## 2. Данные: источник на каждое поле экрана

Экран собирает данные из **трёх** запросов при открытии, остальные
четыре — только по тапу на соответствующий пункт меню.

| Запрос | Что берём | Когда |
|---|---|---|
| `GET /auth/me` | имя, почта — шапка | при открытии |
| `GET /profile/subscription` | тариф, лимиты, расход — блок тарифа | при открытии |
| `GET /profile/charts` | список карт, `primary_chart_id` — «Мои карты» | при открытии |
| `GET /profile/history` | история разборов | по тапу на пункт меню |
| `GET /profile/referral` | код и ссылка приглашения | по тапу на пункт меню |
| `GET /push/settings` | переключатели уведомлений | по тапу на пункт меню |
| `GET /profile/settings` | экспертный режим, день дайджеста | по тапу на пункт меню |

«Следующий тариф» для блока §4 сервера не требует вовсе — источник
теперь чисто локальный, `TIERS` из `constants.js` (решено в §4.1).
Экран «Ещё» тем самым не зависит от наличия у аккаунта хотя бы одной
карты — важно, потому что «нет карт» (§8) само по себе реальное
состояние, и блок тарифа обязан работать и в нём.

Три запроса при открытии (`auth/me`, `subscription`, `charts`) грузятся
параллельно — между ними нет зависимости. Экран открывается, когда
пришли все три; одна упавшая переводит **весь** экран в состояние
ошибки (§8), не отдельный блок — частично собранная шапка/тариф хуже
явного отказа.

`auth/me` дешевле `subscription` (без лимитов/расхода) и достаточен для
имени и почты — поэтому шапка берёт его, а не дублирует поля из
`subscription`.

## 3. Шапка

```
aristea
aristeatime@mail.ru
```

- Имя — `auth/me.name`, крупно. Почта — `auth/me.email`, мельче,
  вторичным цветом. Ровно как в прототипе (`.more-head h3` / `span`).
- Оба поля у сервиса всегда заполнены (проверено: у аккаунта без
  подтверждённой почты `email` всё равно есть — само наличие адреса не
  зависит от `is_email_confirmed`). Пустого состояния для шапки нет.

## 4. Блок тарифа

Формулировка утверждена в прошлой сессии. Пункт про транзиты исключён
из показываемых 4 пунктов — решение 06.09.2026, причина в §4.2, поэтому
пример ниже — уже с исключённым пунктом, не то, что было утверждено
изначально:

```
Ваш тариф
Бесплатный
На Вегу дополнительно:
 · До 5 сохранённых карт одновременно
 · 5 AI-интерпретаций в месяц
 · Планер: рекомендации на месяц
 · Лунный календарь на год
[ Тарифы ]
```

### Источник каждого поля

| Что на экране | Источник |
|---|---|
| «Бесплатный» (название текущего) | `TIER_NAMES[subscription.tier]` — сервер отдаёт id (`"free"`), русское название берём локально |
| «На Вегу дополнительно:» | название следующего тарифа — см. §4.1, источник локальный |
| 4 пункта списка | `tierFeatures(nextTierId)` из `constants.js`, отфильтровано от пункта про транзиты (§4.2) — статический текст, уже написанный людьми, НЕ вычисляется из живых `features`/`limits` |
| Кнопка «Тарифы» | ведёт на `/pricing` на сайте — см. §4.3 |

### 4.1. Откуда берётся «следующий тариф» — решено: `TIERS`, без сети

`TIER_ORDER` в `constants.js` не существует (только упоминание в
комментарии первой строки), а живёт тремя независимыми копиями
(`ProfilePage.jsx`, `backend/feed/horizon.py`, `test_rate_limits.py`).
Четвёртую копию не заводим — но и не тянем чужой источник за неё.

**Решено: `TIERS` из `constants.js`.** Массив уже экспортируется и уже
упорядочен (`free, lite, pro, premium`):

```
nextTierId = TIERS[TIERS.findIndex(t => t.id === currentTier) + 1]?.id ?? null
```

Название — `TIER_NAMES[nextTierId]`, локально, без обращения к серверу.

**Почему не `horizon.next_tier` из ленты (был рассмотрен и отклонён).**
Это поле реальное и с готовым русским названием, но приходит из
`GET /chart/{id}/feed`, а ей нужен `chart_id`. У аккаунта без карт
(состояние «нет карт», §8 — реальное, не гипотетическое) экран «Ещё»
не может выбрать чью ленту запрашивать, и блок тарифа остался бы без
названия следующего уровня ровно тогда, когда важнее всего показать
путь наверх. Экран «Ещё» не должен зависеть от того, есть ли у
аккаунта хоть одна карта, — а `TIERS` от этого не зависит вовсе.

У Ориона (последний тариф, `TIERS`-индекс за пределами массива,
`nextTierId === null`) — блок «На … дополнительно» не показываем
вовсе, только «Ваш тариф / Орион», без кнопки апгрейда (кнопка
«Тарифы» остаётся — путь на витрину нужен и подписчику Ориона, для
управления/сравнения).

### 4.2. `transits_months: 0` — решено: пункт про транзиты исключён из «На … дополнительно»

`TIER_FLAGS["free"]["transits_months"]` равен `0`, но реальный горизонт
транзитов free — 3 месяца через отдельную константу
`FREE_TRANSITS_TEASER_MONTHS`, мимо флага (`MORE_API_RECON.md` §4).

Для блока тарифа это **не задевает** пункты из §4 напрямую: список «На
… дополнительно» берёт текст из `tierFeatures(nextTierId)` — статических
строк в `constants.js`, а не из живого `features.transits_months`. При
проверке 06.09.2026 число там **не оказалось ложью** — «Транзиты:
горизонт 6 месяцев…» для Веги дословно совпадает с
`TIER_FLAGS["lite"]["transits_months"] = 6`, то же для Лиры (12) и
Ориона (24). Диагноз «блок врёт» был снят самим владельцем после
перепроверки.

**Решено: пункт про транзиты всё равно исключён из показываемых 4 пунктов
на этом экране** — не потому что число сегодня неверно, а потому что
горизонт транзитов живёт тремя независимыми копиями одного факта (сам
флаг, `FREE_TRANSITS_TEASER_MONTHS`-исключение для free, статический
текст в `constants.js`), и на free они уже разошлись. Пока источник не
станет один, апселл этого экрана не тычет числом, которое подтверждённо
умеет расходиться в соседнем случае. Реализация — фильтр на клиенте:

```
tierFeatures(nextId).filter(f => !f.startsWith('Транзиты')).slice(0, 4)
```

Только этот экран, `constants.js` и текст сайта (`PricingPage`,
`OrionPage`) не тронуты — они читают тот же `tierFeatures()` напрямую,
без фильтра, и продолжают показывать пункт про транзиты как есть.

**Настоящая починка — задача бэкенда, отдельным заходом.** Три
накопленные правки (эта, сохранение имени карты §5.1, бесплатный разбор
как право на карту) записаны одним списком в `CLAUDE.md` — решение
владельца 06.09.2026 делать их вместе, не в рамках мобильного клиента.
Когда `TIER_FLAGS["free"]["transits_months"]` станет равен `3`, источник
станет один — фильтр в этом файле можно будет снять.

### 4.3. Кнопка «Тарифы» — переход на оплату разрешён

Поправка CLAUDE.md 06.09.2026: с мобильного вести на веб-оплату и
страницу цен можно (RuStore, в отличие от Google Play, это разрешает).
Нативной покупки не делаем.

Кнопка открывает `https://aristeatime.ru/pricing` **во внешнем
браузере** (не во встроенном WebView приложения — оплата на чужом
домене ЮKassa внутри собственного WebView недопустима с точки зрения
доверия и cookies сессии).

**Решено: ставим `@capacitor/browser`.** В проекте сегодня только
`@capacitor/android`, `@capacitor/core`, `@capacitor/preferences` — без
нативного плагина открывать системный браузер было бы `window.open()`,
чьё поведение внутри Android WebView в этом проекте не проверено.
`@capacitor/browser` даёт `Browser.open({ url })` — прямой вызов,
гарантированно системный браузер, без гадания про `window.open()`.

Плагин используется на этом экране дважды — здесь и в §6.2 (переход на
страницу профиля сайта за выгрузкой данных), поэтому один плагин
закрывает обе потребности, вторая (`@capacitor/share`) не нужна вовсе —
см. §6.1, §6.2.

## 5. «Мои карты»

```
Мои карты
☉  ·  15 июня 1990 · Москва
☉  ·  28 мая 1996 · Москва                              ★
```

### 5.1. Имени карты не существует — факт, не баг

`GET /profile/charts` не отдаёт `name`/`label`, и это не пропуск в
конкретном ответе: колонки `name`/`label` в модели `NatalChart`
существуют (`models.py:108-109`), схема `BirthDataInput` принимает
`name` от клиента (`schemas.py:17`), но ни `POST /chart/calculate`, ни
`POST /chart/save-anonymous` не передают его при создании записи, и
**ни одно место в бэкенде** это поле не пишет (`MORE_API_RECON.md` §3,
проверено grep'ом по всему `backend/`). Значение — всегда `NULL`,
подтверждено дважды: в самом списке карт и в `/profile/export`.

**Следующему заходу не считать это дефектом отображения.** Строка
карты собирается из того, что действительно приходит: дата рождения
словами (как в шапке экрана «Карта», §3 `SPEC_CHART_SCREEN.md`) и место
до первой запятой. Имени в макете прототипа («Александр», «Мария») не
будет — заменить нечем.

### 5.2. Метка основной карты

`primary_chart_id` в корне ответа и `is_primary` у каждой карты — оба
поля реальные, но у служебного аккаунта ни одна карта не помечена
(`primary_chart_id: null`, обе `is_primary: false`). Значит состояние
«основная не выбрана» — не гипотетическое, встретится в проде.

Правило показа звезды (`★`, как в прототипе `.saved .star`): у карты с
`is_primary: true`. Если основной нет ни у одной — звезду не показывать
ни у одной; сам список от этого не ломается, порядок карт
(`created_at DESC`, задаётся сервером) не меняется.

Тап по карте **не открывает** её на этом заходе (см. §9) — переход к
просмотру конкретной карты требует переключателя карт на экране
«Карта», которого сегодня нет (`SPEC_CHART_SCREEN.md` §9).

### 5.3. Значки

`.mini` в прототипе — кружок со значком. Берём светило по умолчанию
(`☉`) для всех карт: различать по знаку Солнца потребовало бы отдельного
чтения `planets` каждой карты (список карт их не отдаёт, только даты) —
лишний запрос ради иконки. Не делаем.

## 6. Пункты меню

Ручки живые под все пункты (`MORE_API_RECON.md` §1) — заглушек «нет
API» не будет. Но не у всех пунктов есть куда вести по тапу дальше
самого списка данных. Пятый пункт из разведки, «Скачать мои данные»,
здесь не пунктом меню — решение и причина в §6.2.

| Пункт | Что показываем по тапу | Дальнейшее действие |
|---|---|---|
| История разборов | Список: дата, карта (по дате рождения — см. §5.1), первые слова `preview` **после** чистки от `<section name="…">` | Тап по записи — никуда не ведёт (см. §9: разбора карты в приложении ещё нет, открывать нечего) |
| Друзья | `ref_code`, `ref_url`, счётчик приглашённых, недели награды | Кнопка «Копировать ссылку» — см. §6.1 |
| Уведомления | 5 переключателей (`daily_forecast`, `planner`, `key_transits`, `moon_phases`) + время (`daily_time`) | `PATCH /push/settings`; риск работоспособности — см. §7 |
| Настройки | Переключатель `expert_mode`, выбор дня недели `digest_day_of_week` | `PATCH /profile/settings` |

Пункта «Скачать мои данные» в списке меню **нет** — решение, не
пропуск. См. §6.2.

### 6.1. Друзья — решено: копия в буфер обмена, без `@capacitor/share`

`ref_url` — готовая ссылка. **Решено: кнопка копирует её в буфер
обмена** (не системный шеринг) — стандартным веб-`navigator.clipboard.writeText()`,
без нового плагина. После тапа — подтверждение («Ссылка скопирована»),
тем же приёмом, что уже есть в вебе для похожих действий (Toast).

`@capacitor/share` осознанно не ставим — решение по инфраструктуре
(§4.3): единственный новый плагин (`@capacitor/browser`) закрывает обе
сетевые потребности этого экрана (оплата, §4.3, и переход на выгрузку
данных на сайте, §6.2); копирование ссылки для «Друзей» плагина не
требует вовсе.

⚠️ `navigator.clipboard.writeText()` в некоторых WebView требует
защищённый контекст (`https:` либо `localhost`) — что именно отдаёт
Capacitor как origin приложения, этой разведкой не проверялось, нужна
проверка на устройстве (§10).

### 6.2. Скачать мои данные — решено: пункта в приложении НЕТ, это причина, а не пропуск

**В мобильном приложении выгрузки данных не будет.** Ниже — почему, для
следующего захода, который иначе сочтёт отсутствие пункта недоделкой и
попробует реализовать заново.

Ручка `GET /profile/export` отдаёт JSON в теле ответа, не файл на диск.
Единственный способ показать его пользователю телефона как файл —
получить содержимое авторизованным `fetch` (токен только в заголовке,
внешний `Browser` заголовков не несёт — проверено, см. ниже) и
дальше самим что-то сделать с байтами на устройстве. Рассмотрены и
отклонены четыре способа подряд:

1. **`data:` URI через `Browser.open()`** — отклонён владельцем: в
   Android WebView `data:` часто блокируется, а на крупном экспорте
   (интерпретации по несколько КБ каждая) упирается в ограничение
   длины URL.
2. **Отдельная одноразовая ссылка с бэкенда** (по образцу
   `/share/{token}`) — правка сервера ради одной кнопки клиента,
   отклонена как непропорциональная.
3. **`@capacitor/filesystem`** — второй новый плагин вместо одного,
   отклонён по той же логике, что и `@capacitor/share` (§4.3): цена
   инфраструктуры больше пользы одной редко нажимаемой кнопки.
4. **Нативный мост `addJavascriptInterface`** (JS кодирует ответ в
   base64, передаёт в `MainActivity.java`, тот пишет в
   `MediaStore.Downloads`) — технически рабочий (в отличие от 1–3), но
   отклонён: 40–60 строк нового Java-кода, открытый JS→native канал,
   требующий отдельного ревью на безопасность, плюс собственное
   состояние «недоступно» для Android <29 (`WRITE_EXTERNAL_STORAGE` не
   нужен только начиная с API 29 — при `minSdkVersion 23` в проекте
   часть устройств осталась бы без permission-флоу или без кнопки
   вовсе). Слишком много ради функции, которой пользуются единицы и
   которая уже работает на сайте.

**Что оставлено вместо пункта меню.** Не пустое место и не заглушка —
рядом с «Настройками» одна строка текста: выгрузка данных доступна в
личном кабинете на сайте, с переходом туда через уже поставленный
`@capacitor/browser` (`Browser.open({ url: 'https://aristeatime.ru/profile' })`,
таб «Данные» на веб-странице `ProfilePage.jsx`, где `/profile/export`
уже вызывается и работает, `ProfilePage.jsx:1067`).

**Право на переносимость данных (152-ФЗ) не нарушается.** Оно
реализовано — на сайте, тем же аккаунтом. Мобильное приложение не
обязано дублировать каждую веб-функцию, обязано лишь не прятать, что
она есть и где — строка-ссылка это и делает.

Лимит `3/hour` (`export_key`, `profile/router.py`) и его формат
(`429 {"error":"Rate limit exceeded: 3 per 1 hour"}`, без `Retry-After`
— проверено живьём) документированы здесь для полноты разведки, но
**этому экрану больше не нужны**: состояние «лимит исчерпан» относится
к веб-кабинету, не к мобильному приложению.

### 6.3. Выйти из аккаунта — добавлено 08.09.2026

До этого `logout()` был доступен только вторым ходом на экране ошибки
(«Войти заново», см. CLAUDE.md — «Холодный старт упирается в
ЗАДЕРЖИВАЮЩИЙ лимит»): в штатном режиме человек не мог ни выйти, ни
сменить аккаунт.

Пункт — отдельная строка внизу экрана, **после** списка меню и
переключателя темы, отделена верхней границей (`border-top`) и цветом
`--color-danger`: это не раздел и не настройка, а необратимое действие,
смешивать его с остальным списком нельзя.

**Подтверждение — системный `window.confirm`, не своя модалка.** В
проекте уже есть решение по этому вопросу (`ChartPage.jsx`: «Готового
диалога подтверждения в проекте нет: все существующие подтверждения —
системный `window.confirm` (AdminPage, CRMPage)»), и заводить второй
способ ради одного экрана незачем. В Capacitor его показывает
`BridgeWebChromeClient.onJsConfirm` — нативный `AlertDialog`, ничего
отдельно ставить не нужно, платформы не требуют собственного плагина.

**Выход зовёт готовый `logout()` из `useAuth`, свой не написан.** Тот же
самый вызов, что стоит за «Войти заново» на экране ошибки, — переход на
`/login` происходит одинаково для обоих путей: `logout()` обнуляет
`accessToken`/`user`, `isAuthenticated` становится `false`, и `RequireAuth`
в `MobileApp.jsx` реактивно уводит на `/login` — тем же механизмом, что и
явный разлогин по 401 (`onSessionExpired(logout)`, `useAuth.jsx`). Второго
пути на экран входа не заводилось.

## 7. Уведомления — риск работоспособности

`push.js` подписывается связкой `navigator.serviceWorker` +
`PushManager` + `Notification` (Web Push). Работает ли эта связка внутри
Android WebView Capacitor — **не проверено этой разведкой и не
проверяется без устройства** (`MORE_API_RECON.md` §3).

Экран не должен показывать переключатели уведомлений как будто это
обычный веб-toggle, который просто «может быть выключен пользователем».
Если на старте экрана окажется, что `'serviceWorker' in navigator` (или
`'PushManager' in window`, или `'Notification' in window`) — `false`,
это отдельное, третье состояние блока уведомлений:

```
Push-уведомления недоступны на этом устройстве
```

— вместо переключателей, не рядом с ними. Показывать рабочие тумблеры,
которые сохраняют состояние на сервере (`PATCH /push/settings` не
проверяет возможность WebView), но никогда не приводят к уведомлению, —
хуже честного «недоступно»: человек будет уверен, что подписался.

## 8. Состояния экрана

| Состояние | Что на экране |
|---|---|
| загрузка | скелет: строка шапки, прямоугольник тарифа, 2 плейсхолдера карт, 5 строк меню |
| ошибка запроса | «Не удалось загрузить профиль», текст ошибки, кнопка «Повторить» |
| нет карт у аккаунта | блок «Мои карты» заменяется строкой «Пока нет ни одной карты» — так же, как на экране «Карта» (`SPEC_CHART_SCREEN.md` §8), не отдельная выдумка для этого экрана |

**Любой отказ обязан доводить до кнопки «Повторить», не оставлять
скелет** — то же правило §8 `SPEC_CHART_SCREEN.md`, тот же баг уже был
найден 05.09.2026 в Ленте и не должен повториться здесь.

Экран собирает 3 запроса параллельно (§2) — если упал ровно один
(например, `subscription` при исправных `auth/me` и `charts`), это всё
равно общая ошибка экрана, не частичная отрисовка: показывать имя и
карты без тарифа (или наоборот) не входит в этот заход, частичная
деградация — отдельное решение, не то же самое что «просто попробовать
ещё раз всё целиком».

## 9. Чего в этом заходе нет — и почему

- **Тап по карте не открывает её.** Тот же принцип, что «тап по
  планете» на экране «Карта» (`SPEC_CHART_SCREEN.md` §9): открывать
  нечем, переключателя карт нет.
- **Тап по записи истории не открывает разбор.** Разбор карты в
  приложении вообще не реализован (`SPEC_CHART_SCREEN.md` §1) —
  открывать историю на пустое место хуже, чем не открывать.
- **Выгрузки данных в приложении нет вовсе.** Не забыто и не заглушка
  — четыре способа рассмотрены и отклонены, причины по каждому — в
  §6.2. Вместо пункта меню — строка-ссылка на веб-кабинет.
- **Системный шеринг (`@capacitor/share`)** — осознанно не ставим.
  «Друзья» обходятся копированием в буфер (§6.1), переход за выгрузкой
  данных — тем же `@capacitor/browser`, что и кнопка «Тарифы» (§4.3,
  §6.2). Один новый плагин, не два.
- **Управление подпиской** (отмена, смена тарифа с уменьшением) — кнопка
  «Тарифы» ведёт на сайт, там уже есть весь путь; повторять его в
  приложении не входит в этот заход.
- **Различение карт по знаку Солнца** — см. §5.3.

## 10. Что проверить на устройстве, а не в Chrome

- `Browser.open({ url })` (`@capacitor/browser`) действительно открывает
  системный браузер для обычного `https:` URL — оба назначения этого
  экрана используют один и тот же вид вызова (§4.3, кнопка «Тарифы»;
  §6.2, ссылка на выгрузку данных на сайте), так что один прогон
  проверяет оба места сразу.
- `navigator.clipboard.writeText()` действительно работает в origin,
  который использует Capacitor WebView для этого приложения — не
  предполагать по вебу, где секьюр-контекст не вопрос (§6.1).
- `'serviceWorker' in navigator` и `'PushManager' in window` — что они
  возвращают в реальном Android WebView Capacitor, не в Chrome
  desktop (§7). Разведка это НЕ проверяет в принципе.
- Скелет на 3 параллельных запроса не мигает пустым состоянием между
  приходом первого и последнего ответа (эффект уже описан в
  `SPEC_FEED_SCREEN.md` про одиночные запросы, здесь — тот же риск, но
  для трёх сразу).

## 11. Обновление жестом (pull-to-refresh) — добавлено 08.09.2026

Жест на собственном скроллере экрана (в отличие от «Ленты», которая делит
скроллер с `TabShell`), обновляет те же три запроса, что и при открытии:
`fetchMe`, `fetchSubscription`, `fetchCharts` — то есть в том числе список
«Моих карт», ради которого всё и затевалось.

**Только в корневом виде.** Под-разделы (История, Друзья, Уведомления,
Настройки) монтируются при каждом заходе и грузят себя сами — устаревать им
негде.

⚠️ Полоске задан отрицательный нижний отступ: корень экрана — флекс с
`gap: 20`, и нулевая по высоте полоска всё равно получила бы разрыв, то есть
над шапкой постоянно висели бы лишние 20px. У двух других экранов родитель
без `gap`, там компенсировать нечего.

Устройство жеста и общие решения — SPEC_FEED_SCREEN.md §14.

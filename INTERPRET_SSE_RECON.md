# INTERPRET_SSE_RECON.md — что реально приходит по `GET /chart/{id}/interpret`

Разведка под экран разбора интерпретации в мобильном приложении,
07.09.2026. Спецификация экрана и код в эту работу не входят — здесь
только то, что уже есть на сервере и во что мобильный клиент упрётся.

Опорные документы: CLAUDE.md, раздел «Кэш-хит обязан отдаваться
порциями, иначе фронт разбирает секции неверно», и `CHART_API_RECON.md`
§4 (боевые замеры 05.09.2026 — из них взяты цифры путей 1 и 3, заново
не снимались).

Что здесь **измерено**, а не выведено из чтения кода, помечено явно.
Стендовые прогоны лежали в скратчпаде и в коммит не идут; как их
повторить — в §7.

---

## 1. Общий контракт потока — одинаков на всех трёх путях

```
GET /api/v1/chart/{chart_id}/interpret?ticket=<одноразовый тикет>
→ 200, text/event-stream, Transfer-Encoding: chunked
```

Кадры ровно двух форм плюс терминатор:

```
data: {"text": "<кусок>"}      ← полезная нагрузка, ключ всегда "text"
data: {"error": "<текст>"}     ← отказ, приезжает ВМЕСТО [DONE]
data: [DONE]                   ← успешное завершение
```

Свойства, общие для всех путей и важные для клиента:

- **Поля `id:` сервер не шлёт**, `last_event_id` эндпоинт не принимает
  (`grep` по `main.py` — ни одного вхождения). Значит докачки с места
  обрыва нет: реконнект — это полная перегенерация с нуля. Веб при этом
  ретраит трижды (`_connectSSE`), собирая `lastEventId`, который всегда
  остаётся пустым; см. открытый вопрос №3.
- **Тикет одноразовый** (Redis `GETDEL`, TTL 60 с). На реконнект нужен
  **новый** тикет, старый даст 403.
- **Отказ по лимиту — первое событие потока, а не HTTP-статус**, и
  `[DONE]` за ним не идёт (`main.py:1149-1154`). Сделано потому, что
  `EventSource` не отдаёт JS ни кода ответа, ни тела. Исключение —
  аноним: ему настоящий 403, на этом держится одноразовость тикета.
- **`[DONE]` — единственный признак успеха.** Ветка
  `IncompleteInterpretation` (обрыв или обрезка по длине) шлёт `error`
  и `[DONE]` не шлёт; расход при этом не засчитывается.

## 2. Три пути отдачи и как сервер выбирает между ними

Приоритет жёсткий, проверяется в этом порядке (`main.py:1104-1147`,
затем `interpretation/router.py:393-430`):

```
БД (saved_interpretation)  →  Redis (stream:*)  →  живая генерация
      путь 3                     путь 2                путь 1
```

| | Путь 1 — живая генерация | Путь 2 — Redis-кэш | Путь 3 — сохранённый разбор |
|---|---|---|---|
| Где в коде | `router._try_stream`, `router.py:427` | `router.py:403-422`, через `replay_as_stream` | `main.py:1143-1147`, ранний выход |
| Условие | нет строки в БД и нет ключа в Redis | нет строки в БД, есть ключ `stream:{hash}:{tier}:{model}:{wl}` | `user is not None` **и** есть строка `Interpretation` по этой карте |
| Число `data`-событий | **2365** (замер) | **150** (замер, 1085 слов) | **1** + `[DONE]` (замер) |
| Длительность | **40.4 с** (замер) | ~3.0 с (замер, `delay=0.02` × 150) | ~1.0 с (замер) |
| Размер события | 1–8 символов, по токенам | ≤48 символов (замер), 8 слов | **весь текст целиком**, 7486 символов |
| Теги `<section>` | **разрезаны по токенам**: `<section`, ` name`, `="`, `general`, `">\n` | **каждый тег — отдельное событие**, ни одного смешанного с текстом (замер: 12 тегов, 0 смешанных) | все 12 тегов **внутри одного события** |
| Кто платит | генерация, деньги | ничего | ничего |

Цифры путей 1 и 3 — боевые, `CHART_API_RECON.md` §4 (карта A, free,
1085 слов, 7486 символов, шесть секций). Цифры пути 2 — стендовый
прогон настоящего `replay_as_stream` на тексте той же формы (§7).

### Достижимость путей — не равна их важности

⚠️ **Путь 2 для авторизованного пользователя на той же карте
практически недостижим.** С 30.08.2026 каждый штатно завершённый стрим
пишет строку в `Interpretation` (`_save_chart_interpretation`,
`main.py:996`), а путь 3 проверяется раньше. То есть Redis-кэш
перехватывает запрос только когда строки в БД нет:

- **аноним** (по `access_token` карты) — `saved_interpretation`
  запрашивается только при `user is not None`, поэтому аноним пути 3 не
  видит никогда и уходит в путь 2 или 1;
- **другая карта с тем же `profile_hash`** при том же тарифе, модели и
  `word_limit` — ключ Redis не содержит `chart_id` вовсе
  (`stream:{profile_hash}:{tier}:{model_id}:{wl_key}`);
- строка в БД не записалась (падение записи глушится) или была удалена.

Практический вывод для мобильного: **все три пути живые, ни один нельзя
объявить теоретическим.** Путь 3 — основной для повторного открытия
своей карты, путь 1 — для первого разбора, путь 2 — для анонимов и
совпадающих профилей.

### Что лежит в БД на пути 3

`_save_chart_interpretation` сохраняет `"".join(chunks).strip()` —
**сырой текст модели вместе с тегами `<section>`**, поле `sections`
пишется `None` (`main.py:1023, 1046`). Готовой структуры секций в базе
нет, и разбирать теги придётся клиенту в любом случае — сервер их не
разбирает ни на одном из трёх путей.

### Объём зависит от тарифа

`interpretation_word_limit` — 500 / 800 / 2500 / 5000 слов
(free / lite / pro / premium, `auth/rate_limits.py:43,63,78,93`).
Замеры выше сняты на free. Для путей 2 и 3 это масштабируется линейно:
путь 2 даёт примерно `слов/8 + 12` событий (на Орионе — около 640
событий и ~13 с проигрывания), путь 3 остаётся **одним событием** любой
длины — на Орионе это одна `data:`-строка порядка 35–40 КБ.

⚠️ Отсюда требование к транспорту: **разборщик SSE-строк не должен
предполагать короткие строки.** Одно событие пути 3 больше, чем весь
поток пути 2.

## 3. Что делает вебовский `flushBuffer` на каждом из трёх путей

Стендовый прогон точной копии `flushBuffer`
(`frontend/src/api/client.js:225-254`) вместе с окружающим циклом
`onmessage`, на трёх последовательностях событий из §2. Замер, не
рассуждение.

| Путь | `section_start` | `section_end` | Текст вне секций | Обрывки тегов в тексте |
|---|---|---|---|---|
| 1 — живая генерация | **0** | 6 | **6645 символов, весь** | **12** |
| 2 — Redis `replay_as_stream` | 6 | 6 | 0 | 0 |
| 3 — сохранённый разбор | 6 (все шесть **подряд, до текста**) | 6 | **6480 символов, весь** | 0 |

Путь 2 разбирается правильно — ради этого `replay_as_stream` и
`keep_intact` были сделаны, лечение работает.

Путь 3 ломается ровно так, как описано в CLAUDE.md: шесть
`section_start` подряд до всякого текста, оглавление пустое, весь разбор
приклеивается к последней секции.

### ⚠️ Находка: на живом пути ломается ОТКРЫВАЮЩИЙ тег, а не порядок

CLAUDE.md говорит: «При живой генерации он работает случайно: чанки
мелкие, в буфер попадает не больше одного тега». **Замер это не
подтверждает: на живом пути `section_start` не приходит ни разу.**

Причина — в удержании хвоста внутри `flushBuffer`:

```js
const lastOpen = result.lastIndexOf('<');
if (lastOpen !== -1 && lastOpen > result.length - 20) { … придержать хвост … }
```

Условие сводится к «длина хвоста от `<` **меньше 20 символов**». А
открывающий тег длиннее: `<section name="general">` — 24 символа,
`<section name="relationships">` — 30. Пока тег накапливается по
токенам, буфер проходит через состояние `<section name="general` (22
символа) — хвост уже длиннее 19, удержание не срабатывает, и незакрытый
тег уходит наружу как обычный текст. Дальше приезжает `">` отдельно, и
собрать тег обратно уже нечем.

Закрывающий `</section>` (10–11 символов) в порог укладывается и потому
разбирается верно — отсюда асимметрия 0 против 6 в таблице.

Мелкие чанки — не спасение, а **именно тот случай, в котором эвристика
не работает**: чем мельче нарезка, тем вернее буфер пройдёт через
состояние «незакрытый тег длиннее 19 символов».

**07.09.2026 — подтверждено, открытый вопрос №1 закрыт.** Проверено
дешёвым способом (не живым вебом): дословная копия `flushBuffer`
трассирована вручную, событие за событием, на **буквальных байтах**
чанков из `CHART_API_RECON.md:366-377` (`<section`, ` name`, `="`,
`general`, `">\n` для открывающего тега; `</`, `section`, `>` для
закрывающего) — не на реконструированной форме, а на записанной ранее
последовательности живой генерации.

Результат трассировки открывающего тега: на чанке `general` буфер
становится `<section name="general` (23 символа), условие удержания
`lastOpen(0) > length−20(3)` ложно — хвост **не удерживается** и
целиком уходит наружу как обычный текст двумя порциями:
`<section name="general` и `">\n`. `section_start` не срабатывает.
Закрывающий тег `</section>` (10 символов) укладывается в порог,
собирается целиком, `section_end` срабатывает штатно.

Дальше — по `Interpretation.jsx:206-227`: раз `section_start` не
пришёл, `currentSectionRef.current` остаётся `null` на всём потоке,
весь текст (включая утёкшие обрывки тегов) складывается в один
fallback-блок `{ name: '_intro', title: '' }`. Рендер (строка 378:
`{sec.title && (<h2>…)}`) при пустом `title` заголовок не рисует.

⚠️ **Поправка 07.09.2026: вывод «в прозе видны обрывки тегов» был
неверен, дефект на живом пути замаскирован вторым механизмом.**
Проверено прогоном: утёкшие куски (`<section name="general` и `">\n`)
попадают в ОДИН и тот же текстовый блок и склеиваются там обратно в
`<section name="general">` на отдельной строке. А `renderMarkdown`
(`Interpretation.jsx:102-118`) — независимая от `flushBuffer`
подстраховка — разбирает текст ПОСТРОЧНО и превращает такую строку в
`<h2>` с русским заголовком. Замер на живой последовательности: шесть
строк превращаются в заголовки, обрывков, видных как текст, — ноль.

Значит на живом пути человек видел заголовки и не видел разметки;
сломана была не картинка, а **структура**: массив `sections` состоял из
одного блока `_intro` вместо шести. Отсюда практические следствия —
заголовки приходили из другого словаря (`SECTION_TITLES_RU`, иная
формулировка) и с другим стилем, чем на пути 3, а всё, что читает
`sections` (посекционная анимация, любая будущая навигация по разбору),
работало с одним блоком вместо шести.

Путь 3 при этом был сломан и визуально: шесть секций заводились, но
весь текст доставался последней.

Живым вебом (скриншот с прода) не перепроверялось — трассировка кода на
реальных байтах и прогон редьюсера признаны достаточными, вариант (б)
не понадобился.

## 4. Требования к однопроходному парсеру мобильного клиента

Из §2 и §3. Каждое требование привязано к пути, который его порождает.

1. **Один проход по буферу в порядке встречи.** Не два `replace` подряд:
   именно двухпроходность делает путь 3 неверным даже тогда, когда все
   теги целы. Парсер идёт по буферу слева направо и отдаёт события
   `section_start` / `text` / `section_end` в том порядке, в каком они
   встретились. (Путь 3, и он же корень задачи из CLAUDE.md.)
2. **Состояние живёт между событиями, а не внутри одного.** Тег может
   быть разрезан на произвольное число событий в произвольных местах.
   (Путь 1.)
3. **Удержание незакрытого хвоста — без порога длины.** Если после
   последнего `<` идёт то, что ещё может стать тегом, — придержать
   целиком, сколько бы символов ни накопилось. Порог в 19 символов —
   корень находки §3. Освобождать хвост, когда он **перестал быть
   возможным префиксом** тега (например пришёл символ, которого в этой
   позиции быть не может), а не когда он стал длинным.
4. **Одно событие может содержать весь документ.** Обработка должна быть
   одинаковой для события в 1 символ и в 40 КБ, и внутри одного события
   могут лежать все 12 тегов вперемешку с текстом. (Путь 3.)
5. **Текст до первого `section_start` — легальный случай**, а не ошибка:
   модель может начать с преамбулы вне тегов. Складывать его в
   «нулевую» секцию, а не приписывать первой или молча терять.
6. **Незакрытая секция на `[DONE]` — тоже легальный случай** (обрезка по
   длине, ранний обрыв): закрывать её самим, не теряя накопленный текст.
7. **`[DONE]` обязателен для «готово», `error` — вместо него.** Событие
   `error` закрывает соединение со стороны клиента (иначе на вебе
   получались три реконнекта и «Соединение прервалось» вместо текста
   отказа).
8. **Реконнект — только с новым тикетом и с нуля.** Докачки нет (§1);
   значит либо перезапуск разбора целиком, либо отказ от авто-реконнекта
   в пользу явной кнопки «Повторить».
9. **Имена секций — закрытый список из шести** (`general`, `career`,
   `relationships`, `health`, `finance`, `spirituality`,
   `interpretation/prompts.py:70`), человеческие названия для них там же
   в `SECTION_NAMES`. Неизвестное имя игнорировать нельзя — модель может
   выдать что угодно; показывать как есть или под общим заголовком.
10. **Регулярка тегов должна совпадать с серверной.** Сервер режет по
    `</?section(?: name="[^"]+")?>\n?` (`router.py:33`) — в частности,
    съедает один перевод строки после тега. Разойдётся клиентская —
    появятся лишние пустые строки на путях 2 и 3.

Проверять парсер имеет смысл сразу на трёх записанных
последовательностях (по одной на путь), а не на одной живой: путь 2
проходит через любой разумный парсер, а ломаются пути 1 и 3 — и ломаются
по-разному.

## 6. Открытые вопросы к владельцу

1. ✅ Закрыт 07.09.2026 и **исправлен**: находка §3 подтверждена
   трассировкой на реальных байтах, но её визуальная часть оказалась
   слабее заявленного — см. поправку в §3 (разметку маскировал
   `renderMarkdown`, человек видел заголовки; сломана была структура
   `sections`, а не картинка). Сам разбор переписан:
   `frontend/src/lib/sectionStream.js`, однопроходный, общий для веба и
   мобильного, `flushBuffer` удалён. Требования §4 закрыты все десять,
   тесты — на трёх записанных последовательностях.
2. **Показывать ли на пути 3 анимацию набора?** Сегодня сохранённый
   разбор приезжает одним куском за секунду. Мобильный клиент может
   отрисовать его сразу (честно и быстро) или проигрывать по словам
   ради единообразия с живой генерацией. Это продуктовое решение, из
   кода не выводится.
3. **Что делать при обрыве посреди живой генерации?** Докачки нет,
   тикет одноразовый, повтор — это заново 40 секунд и, если строка в БД
   не записалась, заново деньги. Варианты: авто-реконнект как на вебе,
   явная кнопка «Повторить», или показ частичного текста с пометкой.
   Мой выбор по умолчанию — кнопка, но это стоит подтвердить.
4. **Нужен ли мобильному экрану кейс анонима?** От этого зависит,
   попадёт ли путь 2 в приёмку вообще: у авторизованного пользователя на
   своей карте он почти недостижим (§2).
5. **Держать ли парсер общим с вебом?** Однопроходный парсер закрывает
   все три пути и для веба тоже. Написать его один раз в общем месте
   (как сделали с `ruDeclension.js`) дороже сейчас, но снимает вторую
   копию правила разбора тегов. Или мобильный пишет свой, а веб чинится
   отдельной задачей.

## 7. Как повторить замеры

Оба стенда — одноразовые скрипты в скратчпаде сессии, в репозиторий не
кладутся. Что они делают, чтобы можно было собрать заново:

**Путь 2, нарезка `replay_as_stream`** — импортировать настоящую функцию
из `backend/async_utils.py`, скормить ей текст формы «6 секций по ~180
слов с тегами `<section name="…">`», передать
`keep_intact=re.compile(r'</?section(?: name="[^"]+")?>\n?')` (та же
регулярка, что в `router.py:33`) и посчитать порции: получилось 150
порций, из них 12 — чистые теги, 0 — теги, склеенные с текстом,
максимум 48 символов на порцию.

**§3, поведение `flushBuffer`** — скопировать функцию из
`frontend/src/api/client.js:225-254` дословно вместе с логикой

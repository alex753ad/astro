# Разведка боевых ручек под экран «Карта»

Дата: 05–06.09.2026. Все ответы ниже — **реальные**, сняты запросами к
`https://www.aristeatime.ru/api/v1` служебным аккаунтом из `.env`.
Скрипты разведки одноразовые, в репозиторий не клались.

## Условия прогона

```
аккаунт   : aristeatime@mail.ru
user_id   : 1bcbb20b-6ff2-4dc1-bd51-b5cecc034e18
тариф     : free
карта A   : b1ae94f2-d64f-4f31-81e2-8555ca8a1e37  (1990-06-15, 14:30, Москва)
карта B   : 5b86294d-74c6-4ae6-b722-b375793323ee  (1996-05-28, 11:50, Москва)
```

У аккаунта **две** карты, обе сняты. Структура ответа у них совпадает
до ключа (`set(A) ^ set(B) == set()`), различаются только значения.

⚠️ **Прогон изменил состояние аккаунта:** на карте A израсходован
бесплатный разбор (`free_interpretation_used: false → true`,
`has_interpretation: false → true`). Это было необходимо, чтобы ответить
на вопрос «что приходит на free» и проверить поведение при ПОВТОРНОМ
запросе. На карте B бесплатный разбор не тронут — право оказалось
**на карту**, а не на аккаунт (см. §4).

# 1. Какие ручки отдают данные карты

Пути в бэкенде объявлены в `backend/main.py` (`@app.get`/`@app.post` с
полным префиксом `/api/v1`) и в `backend/profile/router.py`
(`APIRouter(prefix="/api/v1/profile")`). Grep по `frontend/src` на
URL-пути (не по именам обёрток) даёт те же адреса — прямых вызовов мимо
`api/client.js` по карте нет, кроме `ChartPage.jsx`, который ходит
`fetch` напрямую.

| Метод | Путь | Что делает | Авторизация | Тарифный гейт |
|---|---|---|---|---|
| POST | `/chart/calculate` | считает и СОХРАНЯЕТ новую карту | опциональна (аноним → `user_id NULL`) | **да** — `profiles_limit`, 403 |
| GET | `/chart/{id}` | читает сохранённую карту целиком | да (или `X-Chart-Token`) | нет |
| GET | `/profile/charts` | список карт аккаунта | да | нет (лимит на создание, не на чтение) |
| DELETE | `/profile/charts/{id}` | удалить карту (освобождает слот) | да | нет |
| PATCH | `/profile/primary-chart` | пометить карту основной | да | нет |
| GET | `/chart/{id}/interpret` | разбор карты, **SSE** | да, по одноразовому тикету | да, см. §4 |
| POST | `/chart/{id}/interpret` | тот же разбор, без стрима | да | да |
| GET | `/profile/history` | история разборов | да | нет |
| GET | `/profile/subscription` | тариф + флаги + расход | да | — |
| POST | `/chart/{id}/pdf` | PDF-отчёт | да | `pdf_per_month` |
| POST | `/chart/save-anonymous` | привязать анонимную карту к аккаунту | да | да |

Экрану «Карта» из этого списка нужны три: `/profile/charts` (какую
карту показывать), `/chart/{id}` (данные для колеса и таблиц),
`/chart/{id}/interpret` (разбор). Остальное — соседние экраны.

## Что отвечает каждая на самом деле

```
GET  /chart/{id}            без токена          → 404 {"detail":"Chart not found: <id>"}
GET  /chart/{id}            с токеном           → 200
POST /chart/calculate       на потолке в 2 карты → 403
     {"detail":"Достигнут лимит сохранённых карт (2) для тарифа Бесплатный.
       Удалите ненужную карту, чтобы освободить место, или перейдите на
       старший тариф на странице /pricing."}
```

404 вместо 403 на чужой/несуществующей карте — намеренно
(`resolve_chart_access`, одинаковый ответ на «нет карты» и «нет
доступа»).

## CORS: webview с origin `https://localhost` проходит

Проверено живьём, не по конфигу:

```
OPTIONS /chart/{id}   Origin: https://localhost
→ 200
  access-control-allow-origin:      https://localhost
  access-control-allow-credentials: true
  access-control-allow-methods:     GET, POST, PATCH, DELETE, OPTIONS
  access-control-allow-headers:     Accept, Accept-Language, Authorization,
                                    Content-Language, Content-Type,
                                    X-Chart-Token, X-Client-Platform
  access-control-max-age:           600
```

# 2. Полный ответ `GET /chart/{id}`

Верхний уровень — 19 полей, никакой обёртки:

```
access_token, ascendant, aspects, birth_date, birth_place, birth_time,
free_interpretation_used, has_interpretation, house_system, houses, id,
latitude, longitude, midheaven, name, planets, time_unknown, timezone,
warnings
```

Мета карты A целиком:

```json
{
  "id": "b1ae94f2-d64f-4f31-81e2-8555ca8a1e37",
  "name": null,
  "birth_date": "1990-06-15",
  "birth_time": "14:30",
  "birth_place": "Москва, Центральный федеральный округ, Россия",
  "latitude": 55.625578,
  "longitude": 37.606392,
  "timezone": "Europe/Moscow",
  "time_unknown": false,
  "house_system": "placidus",
  "warnings": [],
  "access_token": null,
  "has_interpretation": true,
  "free_interpretation_used": true

```

`name: null` — имя карты не заполнено, хотя при создании передавалось.
Заголовок экрана («Александр» в прототипе) из этого поля взять нельзя,
пока оно пустое; есть только дата, время и место.

## Планеты

**12 точек, всегда одни и те же, в фиксированном порядке:**

```
Sun, Moon, Mercury, Venus, Mars, Jupiter, Saturn, Uranus, Neptune, Pluto,
North Node, South Node
```

**Хирона нет. Лилит нет.** Есть оба узла (Южный — зеркало Северного,
`longitude + 180`, тот же `degree_in_sign`).

Полный список карты A, как приходит:

```json
 {"number":  6, "sign": "Pisces",    "degree": 343.6062},
 {"number":  7, "sign": "Aries",     "degree":   5.7068},
 {"number":  8, "sign": "Aries",     "degree":  29.3523},
```

## Углы

`ascendant` и `midheaven` — отдельные объекты, оба сразу в двух видах:

```json
"ascendant": {"sign": "Libra",  "degree":  5.7068, "longitude": 185.7068}
"midheaven": {"sign": "Cancer", "degree":  7.8593, "longitude":  97.8593}
```

Здесь `degree` — уже градус ВНУТРИ знака (в отличие от домов), а
абсолютная долгота лежит отдельным полем `longitude`.

**Dsc и IC не приходят вовсе.** Выводятся двумя способами, оба точные:
`Dsc = Asc + 180°`, `IC = MC + 180°`, либо просто куспиды 7-го и 4-го
домов — в ответе они совпадают до знака (`houses[6].degree == 5.7068`,
`houses[3].degree == 277.8593 == 97.8593 + 180`).

## Аспекты

**Приходят готовым списком, считать на клиенте не нужно.** У карты A их
23, у карты B — 20. Одно поле в поле:

```json
{"planet1": "Moon", "planet2": "Neptune", "aspect_type": "sextile",
 "angle": 60.8048, "orb": 0.8048, "applying": false, "importance": "high"}
```

- **типы** (все пять, встречаются все): `conjunction`, `sextile`,
  `square`, `trine`, `opposition`. На карте A: trine 7, sextile 6,
  square 5, opposition 4, conjunction 1;
- **орб есть** — `orb`, десятичный, в градусах (0.0 … 7.7 на карте A);
- **точный/расходящийся есть** — `applying: true/false`;
- **важность есть** — `importance`: `high` / `medium` / `low`. Это
  готовый признак для фильтра «показывать только значимые», считать
  ничего не надо.

Аспекты к углам (Asc/MC) в список **не входят** — только планета к
планете. Пара `North Node ↔ South Node` в списке есть и всегда даёт
оппозицию с орбом 0.0: это артефакт расчёта (узлы по определению
напротив друг друга), в списке аспектов на экране её лучше не
показывать.

## Знаки — везде английские

```
Gemini, Pisces, Taurus, Aries, Cancer, Capricorn, Scorpio, Aquarius,
Leo, Libra, Virgo
```

В планетах, домах, `ascendant` и `midheaven` — **одинаково английские**.
Того разнобоя, что нашли в ленте (у фазы Луны знак приходил русским
словом, у транзита английским), здесь **нет**: эта ручка последовательна.

Русские названия — целиком на клиенте. В мобильном они уже есть:
`SIGN_RU` в `frontend/src/mobile/lib/feedTime.js` (именительный) и
`SIGN_PREPOSITIONAL` там же (предложный).

## Время и таймзона

```
"birth_date": "1990-06-15"     — календарная дата, строка
"birth_time": "14:30"          — местное время рождения, строка HH:MM
"timezone":   "Europe/Moscow"  — IANA-имя зоны
"time_unknown": false
```

**Готового UTC-смещения в ответе нет.** Ни `+03:00`, ни `birth_utc`.
Исторический офсет (в июне 1990 Москва жила по летнему времени, UTC+4)
применён на сервере при расчёте — в ответе видно только результат
(положения планет), сам сдвиг наружу не отдаётся. Показать на экране
«14:30 (UTC+4)» без своей таблицы исторических зон нельзя. Для подписи
годится ровно то, что пришло: `14:30`, `Europe/Moscow`.

При `time_unknown: true` (в этом аккаунте таких карт нет) сервер
считает дома на 12:00 и кладёт предупреждение в `warnings` — у обеих
снятых карт `warnings: []`.

# 3. Что закрыто тарифом free

**Сама карта — не закрыта ничем.** Ответ `GET /chart/{id}` на free
приходит полным: все 12 планет, все 12 домов, все аспекты, оба угла.
Ни одного пустого поля, ни одного `locked`, никакой заглушки. Блюрить
на экране «Карта» **нечего** — в отличие от ленты и планера.

Флаги тарифа, как их отдаёт `GET /profile/subscription` (снято живьём):

```json
{
  "tier": "free",
  "features": {
    "interpretation_word_limit": 500,
    "interpretations_per_month": 0,
    "first_interpretation_free": true,
    "first_interpretation_available": true,
    "profiles_limit": 2,
    "transits_months": 0,
    "transits": false,
    "planner_months": 0,
    "lunar_months": 1,
    "pdf_export": true,
    "pdf_per_month": 1,
    "synastry": false,
    "rag_chat": false,
    "crm": false,
    "ai_engine": "deepseek-v4-pro"
  },
  "usage": {
    "ai_interpretations_this_month": 0,
    "transit_ai_this_month": 0,
    "pdf_this_month": 0,
    "charts_this_month": 2
  }
}
```

Что из этого реально трогает экран «Карта»:

| Флаг | Значение | Как проявляется |
|---|---|---|
| `profiles_limit: 2` | обе карты уже созданы | новая карта → **403 с текстом**, экран «Карта» на free не может добавить третью |
| `first_interpretation_free: true` | право на разбор | по одному разбору **на карту**, не на аккаунт (проверено) |
| `interpretations_per_month: 0` | после бесплатного | второй разбор той же карты берётся из БД, новый — по лимиту |
| `interpretation_word_limit: 500` | **не соблюдается буквально** | фактический разбор на free — **1085 слов** (см. §4) |

Последняя строка — ровно тот случай, о котором предупреждали в задании:
верить ответу, а не таблице. `interpretation_word_limit` — это параметр
промпта, а не жёсткий обрез: модель написала вдвое больше, и ответ
пришёл целиком.

# 4. Интерпретация — `GET /chart/{id}/interpret` (SSE)

## Работает ли из webview

Да. Проверено запросом с `Origin: https://localhost` и заголовком
`X-Client-Platform: mobile`:

```
HTTP 200
Content-Type: text/event-stream; charset=utf-8
Transfer-Encoding: chunked
cache-control: no-cache
access-control-allow-origin: https://localhost
access-control-allow-credentials: true
```

`X-Accel-Buffering: no` ставится приложением; в ответе через nginx его
не видно, но поток реально идёт порциями (первое событие через 2.5 с,
дальше по 30–40 мс) — буферизация не мешает.

## Тикет обязателен

`EventSource` не умеет слать заголовок `Authorization`, поэтому:

```
POST /auth/sse-ticket        (с обычным Bearer-токеном)
→ 200 {"ticket": "1Xd9xm842IfvDFno2wYiLmxPOrc2-Cd1d_3IcyNAiVY", "expires_in": 60}

GET  /chart/{id}/interpret?ticket=<ticket>
```

Тикет **одноразовый** (Redis `GETDEL`) и живёт 60 секунд. Практическое
следствие для мобильного: тикет надо брать непосредственно перед
подключением, а при реконнекте — брать **новый**; повторное
использование того же даст 403. Веб делает ровно это
(`_sseTicket()` → `buildUrl()` в `api/client.js`).

## Формат потока

Событий одного вида: `data: {"text": "<кусок>"}`, в конце —
`data: [DONE]`. Ключ у всех событий один (`text`); поле `error`
появляется только в отказных ветках.

Живая генерация, карта A, free (первый прогон):

```
[2.484] data: {"text": "<section"}
[2.484] data: {"text": " name"}
[2.484] data: {"text": "=\""}
[2.647] data: {"text": "general"}
[2.648] data: {"text": "\">\n"}
[2.648] data: {"text": "Т"}
[2.683] data: {"text": "ы"}
…
        data: {"text": "</"}
        data: {"text": "section"}
        data: {"text": ">"}
        data: [DONE]
```

```
всего data-событий : 2365
длительность       : 40.4 с
собранный текст    : 7486 символов, 1085 слов
секции             : general, career, relationships, health, finance, spirituality
```

**Разметка `<section name="...">` приходит и здесь**, ровно как в
описании CLAUDE.md — шесть секций, теги режутся по токенам вместе с
текстом.

## ⚠️ Повторный запрос приходит ОДНИМ куском

Второй запрос той же карты (карта A, через две минуты после первого):

```
всего строк потока : 4
длительность       : 1.0 с

data: {"text": "<section name=\"general\">\nТы человек, в котором уживаются
       две сильные тяги: … <весь разбор целиком, 7486 символов> …</section>"}
data: [DONE]
```

Это **не** тот кэш, о котором говорит CLAUDE.md в разделе «Кэш-хит
обязан отдаваться порциями». Тот раздел про Redis-кэш роутера
интерпретаций и лечение через `replay_as_stream`. Здесь работает
**третий путь**: `backend/main.py`, ветка `saved_interpretation` —
готовый разбор берётся из таблицы `Interpretation` в БД и отдаётся
одним событием сознательно, о чём в коде стоит комментарий:

> «Сохранённый разбор: одно событие с текстом и `[DONE]`. Формат тот же,
> что у живого стрима — клиент копит текст в буфер и сбрасывает его по
> `[DONE]`, ему безразлично, пришёл текст одним куском или сотней.»

Комментарий верен для того клиента, который просто копит буфер. Но
`flushBuffer` в `frontend/src/api/client.js` разбирает секции **в два
прохода в пределах одного события** — и на таком куске (шесть
`<section>` подряд в одном событии) он выдаст шесть `section_start`
до всякого текста. Это ровно тот симптом, который в CLAUDE.md описан
как «оглавление пустое, весь разбор в последней секции».

**Факт зафиксирован, правок бэкенда не предлагаю** (задание это
запрещает). Для мобильного экрана практический вывод один: **свой
разборщик секций должен быть однопроходным** и переживать случай
«весь текст в одном событии». Веб-овский `flushBuffer` в мобильное
приложение переносить нельзя.

## Что приходит на free

- **Первый разбор карты — настоящий**, от DeepSeek (`engine: "deepseek"`
  в `/profile/history`), 1085 слов, шесть секций. Шаблона не было.
- Право — **на карту, а не на аккаунт**: после разбора карты A у карты B
  `free_interpretation_used` остался `false`.
- `usage.ai_interpretations_this_month` при этом **не вырос** (остался 0)
  — бесплатный разбор не считается месячным расходом.
- Повторное открытие уже разобранной карты **бесплатно и без лимита**:
  отдаётся сохранённый текст (см. выше), генерации нет.
- Ветку «лимит исчерпан» снять живьём не удалось: у обеих карт право
  либо ещё есть, либо уже потрачен и потому возвращается сохранённый
  текст. По коду отказ приезжает **первым событием потока**, а не
  HTTP-статусом: `data: {"error": "<текст>"}` без `[DONE]` — так
  сделано потому, что `EventSource` не даёт JS ни кода ответа, ни тела.

# 5. Чего не хватает для экрана из прототипа

Прототип, ЭКРАН 2 (`aristea-mobile.html`, строки 367–462): колесо с
секторами стихий, линиями аспектов и планетами по кругу; шторка снизу с
тремя вкладками «Планеты / Дома / Аспекты»; в списке планет — знак,
градус «6° 29′ 09″» и метка `R`.

| Что на прототипе | Есть в данных? | Комментарий |
|---|---|---|
| Планеты по кругу | **да** | `longitude` 0–360 — прямо угол на колесе |
| Значок планеты | **да**, но не из API | глифы уже лежат в `mobile/lib/feedGlyphs.js` |
| Цвет планеты | **нет в API** | палитра есть в вебе (`PLANET_COLORS`, `NatalChart.jsx`) |
| Метка `R` | **да** | `retrograde: true` |
| Знак планеты | **да**, английский | русское имя — из `SIGN_RU` на клиенте |
| Градус `6° 29′ 09″` | **нет** | приходит `24.0699` — минуты и секунды **собирать самим** |
| Дома, куспиды | **да** | `houses[].degree` — абсолютная долгота, готовая к рисованию |
| Asc / MC | **да** | отдельными полями |
| Dsc / IC | **нет** | считать: `+180°` или брать куспиды 7 и 4 |
| Линии аспектов | **да** | список готов, координаты концов — из `longitude` планет |
| Цвет аспекта | **нет в API** | по типу, правило уже есть в `mobile/lib/feedGlyphs.js` (`aspectColor`) |
| Орб аспекта | **да** | `orb`, десятичный |
| Сектора стихий | **нет в API** | стихия выводится из знака: индекс знака % 4 |
| Имя владельца карты | **нет** | `name: null`; в шапке остаются дата, время, место |
| Часовой пояс подписью | частично | есть `Europe/Moscow`, но **нет** готового `UTC+4` для 1990 года |

**Считать на клиенте придётся ровно четыре вещи**, все арифметические:

1. **Градусы в минуты и секунды.** `24.0699° → 24° 04′ 12″`
   (`m = frac*60`, `s = frac(m)*60`). Ни округления до минут, ни
   готовой строки сервер не даёт.
2. **Dsc и IC** — прибавить 180° к Asc и MC.
3. **Градус куспида внутри знака** — `houses[].degree % 30`
   (у планет уже готов, у домов нет).
4. **Стихия знака** — по индексу знака в зодиаке, для секторов колеса.

Всё остальное — уже в ответе.

# 6. Веб-колесо: переиспользовать или рисовать своё

`frontend/src/components/NatalChart.jsx`, 797 строк.

**Первое, что нужно поправить в постановке: D3 там нет.** Колесо
нарисовано вручную обычным SVG (`<circle>`, `<path>`, `<text>`,
тригонометрия в `useMemo`), а из библиотек подключён только
`framer-motion` (анимация появления) — он уже в зависимостях проекта.
То есть «переиспользовать» не тянет за собой D3-граф.

**Что в нём уже сделано ровно под мобильный сценарий:**

- **щипковый зум и вращение двумя пальцами** — `handleTouchStart` /
  `handleTouchMove` со `scale` до 4× и поворотом, плюс сброс по
  двойному тапу;
- **компактный режим** — `isCompact` даёт `SIZE = 320` вместо 560,
  убирает тики и линии аспектов (порог `< 768px` вычисляется внутри);
- **тёмная тема** — проп `dark`, палитра уже разведена по темам;
- **подсветка** — пропы `highlightPlanet` / `highlightAspect` и колбэк
  `onHoverPlanet`: тап по планете снаружи уже поддержан, свой обработчик
  дописывать не нужно;
- **шрифт значков** — те же два сабсета Noto, что носит мобильное
  приложение, подключаются внутри компонента через `?inline`
  (data-URI), то есть **третьей копии шрифта не появится**.

**Что придётся учесть при переиспользовании:**

- компонент тянет `framer-motion`, которого в мобильном бандле сейчас
  нет вовсе — это +~50 КБ gzip к 66 КБ текущего бандла;
- внутри есть онбординг-тултипы с `localStorage` и кнопка «Показать
  полную карту» — для мобильного экрана это лишнее и потребует либо
  пропа-выключателя, либо ветки;
- размер жёстко 320 или 560; экран телефона шире 320 и колесо должно
  тянуться на всю ширину — понадобится либо третий размер, либо
  внешнее масштабирование обёрткой;
- палитра берётся из CSS-переменных веба (`--tt-*` и хардкод стихий), а
  мобильные токены живут в `mobile/mobile.css` — часть цветов
  разъедется, если не передать их пропами.

**Вывод: переиспользовать, а не рисовать заново.** Готовы самые дорогие
части — тригонометрия колеса, зум щипком, тап по планете, значки. Всё,
чего не хватает, — это обёртка: свой размер, свои цвета, выключенный
онбординг. Написать своё колесо с нуля значит второй раз сделать ту же
тригонометрию и второй раз отладить жесты, а потом держать две
расходящиеся реализации — тот самый класс дефектов, о котором CLAUDE.md
предупреждает отдельно.

Единственный довод против — вес `framer-motion` в мобильном бандле. Он
решается либо пропом «без анимации» с условным импортом, либо
разрешением этого веса: 50 КБ на приложение, которое и так тянет
восемь woff2.

```
POST /auth/login                      → access_token (15 мин)

GET  /profile/subscription            → флаги и расход
GET  /chart/{A}                       → полный ответ
GET  /chart/{B}                       → полный ответ, сверка ключей
GET  /chart/{A}   без токена          → 404
OPTIONS /chart/{A} Origin=https://localhost → CORS
POST /chart/calculate                 → 403 (лимит карт)
POST /auth/sse-ticket                 → тикет, TTL 60 с
GET  /chart/{A}/interpret?ticket=…    → живая генерация, 2365 событий
GET  /chart/{A}/interpret?ticket=…    → повтор: 1 событие целиком
GET  /profile/history                 → запись о разборе, engine=deepseek
```

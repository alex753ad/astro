## 1. `calendar/export_router` не зарегистрирован — исправлено

Подтверждено дословно: `backend/calendar/export_router.py` объявляет
`POST /api/v1/calendar/export-log`, в `main.py` не было ни импорта, ни
`include_router` для него. Фронт (`useGoogleCalendar.js:151`) звал ручку
fire-and-forget с `.catch(console.warn)` — 404 гасился в консоли молча.

**Схема совпадала до правки** — сверил `ExportLogRequest` (роутер) с
`CalendarExportLog` (`models.py:497`) поле в поле: `month`, `event_count`,
`event_types`, `status`, `error_msg` — идентичны, `user_id` роутер
подставляет сам из JWT. Правки моделей не потребовалось.

**Правка**: `backend/main.py` — импорт + `app.include_router(...)`, по тому
же паттерну, что остальные роутеры (`from ... import router as X_router`).

**Коммит**: `47b23b6`. **Тест**: `test_calendar_export_log.py`, 4 теста —
регистрация (раньше 404, теперь 201), запись реально попадает в БД,
401 без авторизации, 422 на плохой `status`.

**Как проверить на проде**:
```bash
curl -X POST https://astreatime.ru/api/v1/calendar/export-log \
  -H "Authorization: Bearer <токен>" -H "Content-Type: application/json" \
  -d '{"month":"2026-09","event_count":1,"event_types":["new_moon"],"status":"success"}'
```
Ожидается `201 {"ok": true}` (раньше — `404`). Дальше:
```sql
SELECT * FROM calendar_export_logs ORDER BY created_at DESC LIMIT 5;
```
Строка должна появиться сразу после первого реального экспорта в Google
Calendar с фронта.

## 2. Флаг `synastry` у Ориона — не правил, предлагаю выбор

Подтверждено, находка живая: `TIER_FLAGS["premium"]["synastry"] = True`
(`rate_limits.py:102`), но `POST /chart/synastry` и `/synastry/interpret`
по-прежнему за `require_admin` (`advanced_charts_router.py:438, 454`),
страница редиректит не-админа (`SynastryPage.jsx:261`). Вреда пользователю
подтверждённо нет — фронт этот флаг вообще не читает: пункт меню
показывается по `user?.is_admin` (`App.jsx:244, 360`), не по флагу, а в
`useAuth.jsx:102` для него жёстко стоит дефолт `false`, не подставляемый
из ответа сервера. Флаг — данные, которые никто не потребляет, но которые
утверждают неправду о самих себе.

**Два варианта, оба минимальны:**

**А. Снять флаг до готовности фичи** (`"synastry": False` у premium),
вернуть `True` тем же PR, что снимает `require_admin`.
- Плюс: `TIER_FLAGS` — «единственный источник истины» по определению из
  CLAUDE.md, и после этой правки снова говорит правду в каждый момент
  времени, а не только пока никто не смотрит.
- Плюс: если завтра кто-то (человек или будущий рефакторинг) решит читать
  этот флаг на фронте буквально — «Орион, значит показываем пункт меню
  всем» — правки не потребуется откатывать, всё уже соответствует
  реальности.
- Минус: чисто формальный — по факту сегодня ничего не меняется, ни один
  потребитель флага не существует.

**Б. Оставить `True`, но пометить.** Комментарий вида `# TODO: синастрия
не готова, эндпоинты за require_admin — не убирать флаг раньше готовности
фичи, см. AUDIT`.
- Плюс: не нужно помнить вернуть флаг обратно при запуске фичи — он уже
  стоит.
- Минус: единственный источник истины продолжает врать, и полагаться
  придётся на то, что читающий обязательно наткнётся на комментарий —
  ровно то условие, которое в этом проекте уже подводило (`profiles_limit`
  vs `charts_per_month`, `FREE_TRANSITS_TEASER_MONTHS` до 31.08.2026).

**Рекомендую А** — по прецеденту из этого же проекта: здесь уже несколько
раз чинили ровно обратную ситуацию (флаг/число говорит неправду, а
починка — исправить сам источник, не комментарий рядом). Держать
известную неправду в `TIER_FLAGS` — прецедент, которым потом можно
оправдать следующую такую же находку. Не правил — жду решения владельца.

## 3. Дубль в превью шаринга — исправлено

Причина не та, что предполагалась в задании: **не** `og:title` совпадает с
`og:site_name` (это разные теги: `"Натальная карта · ..."` vs `"Astrea
Timeline"`, они не совпадают и не могут визуально дать увиденный дубль).
Настоящая причина — `og_title` строился как:
```python
name = chart.share_name or "Натальная карта"
og_title = f"Натальная карта · {name}"
```
Фолбэк для отсутствующего `share_name` — та же строка, что и жёсткий
префикс. При этом **`share_name` не передаёт НИ ОДИН вызывающий на
фронте** — оба места, зовущие `POST /charts/{id}/share`
(`ChartPage.jsx:416, 442`), делают это без параметра. То есть дубль
получал не край­ний случай, а буквально каждая ссылка, когда-либо
отправленная в Telegram.

**Чем заменил, и почему не `chart.name`**: у карты есть два разных поля —
`name` (реальное имя человека, вводится при создании карты) и
`share_name` (`models.py:132`, с комментарием «имя для публичной
страницы» — отдельное, opt-in). Подставлять `chart.name` в публичный,
краулящийся мессенджерами превью значило бы публиковать настоящее имя
человека без его согласия по умолчанию — вероятная причина, почему поля
вообще разделили. Вместо дубля — солнечный знак (`sun`), который и так уже
считается для описания чуть ниже: публичный, узнаваемый, не пустой почти
никогда.

**Коммит**: `c7ad512`. **Тест**: добавлен
`test_no_share_name_uses_sun_sign_not_duplicate_title` в
`test_share_page.py` — фиксирует именно то состояние, которое сегодня
реально на проде (share_name пуст), а не только сценарий с явным именем,
который уже был покрыт.

**Как проверить на проде**: создать ссылку «Поделиться» на любой карте
(без явного ввода имени — интерфейс его и не запрашивает) и вставить
`https://astreatime.ru/chart/share/<token>` в поле сообщения Telegram.
Ожидается превью с заголовком вида «Натальная карта · ♊ Близнецы» (знак —
свой для каждой карты), не «Натальная карта · Натальная карта».

## 5. Индекс на `client_profiles.astrologer_id` — добавлен

Подтверждено: колонка была без `index=True`, при этом
`ClientProfile.astrologer_id == astrologer.id` — фильтр в буквально каждой
ручке CRM: список клиентов и карточка (`crm/router.py:153, 297, 319, 404,
461`), дашборд (`crm/dashboard_router.py:60, 155, 211, 482, 532, 554, 572,
606, 614, 683`), рассылки (`tasks.py:384`). Это не редкий отчётный запрос —
это граница изоляции между астрологами, проходимая на каждый просмотр
списка клиентов. Без индекса — полный скан таблицы по всем астрологам
разом при каждом таком запросе.

**Коммит**: `02c3738`, миграция
`051_client_profiles_astrologer_id_index.py` (идемпотентна). Тест
`test_client_profiles_index.py` — 2 теста: индекс объявлен на уровне
модели SQLAlchemy и реально создаётся в БД (проверено на SQLite тестовой
схемы; на Postgress-проде подтверждает `check-migrations` в CI и команда
ниже).

**Как проверить на проде**:
```sql
\d client_profiles
```
Ожидается строка вида `"ix_client_profiles_astrologer_id" btree
(astrologer_id)` в списке индексов. Опционально, если нужен количественный
эффект:
```sql
EXPLAIN ANALYZE SELECT * FROM client_profiles WHERE astrologer_id = <id>;
```
До миграции — `Seq Scan on client_profiles`, после — `Index Scan using
ix_client_profiles_astrologer_id`.
